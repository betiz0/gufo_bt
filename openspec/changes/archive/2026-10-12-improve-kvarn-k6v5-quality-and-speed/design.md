# Design

## Context

動機は proposal.md を参照。ここにはアプローチを決めるために確認した現状と制約だけを書く。

### 読み出しと書き込みの現行構造（読み取り確認済み）

- decode は `kvarn_read.hip` の `KvarnWalkPartition`（`src/models/qwen/hip/kernels/kvarn_read.hip:418-519`）を online（`QwenKvarnDecodeOnlineKernel`、`:527`）と split-K（`QwenKvarnSplitKPartialsKernel`、`:621`）が共有する。因果検証（`QwenKvarnCausalDecodeKernel`、`:806`）は共有ウォーカーを使わず、`KvarnFoldKeyQuery`/`KvarnBlockOpen`/`KvarnBlockWeight` と値畳み込みヘルパで同じ順序を複製している（`:963-1021`）。`kTileTokens=128`・`kKeyBlock=1`・`kCausalChunk=kKeyBlock` で、因果はキー 1 個ごとに `__syncthreads`（`:944`、`:1069`）と要素ごとの `KvarnUnpackCode`（`:908-938`）を行う。
- GQA はクエリヘッド基準のグリッドで、KV ヘッドごとに 6 個のクエリヘッド CTA が同じ KV を独立に読む（`:527-554`、`tools/qwen27b/kvarn_read_compute_bench.hip:46-50`）。タイル展開のクエリヘッド間共有はない。
- タイルメタデータは通常ウォークでは概ねタイル単位に集約済み（`docs/models/qwen3.8-27b/EXPERIMENTS.md:104`）。K のスケール・ゼロ点はクエリへ折り込み（`:181-205`）、K/V のトークンスケールはキーごと（`:499`、`:507`）、V はトークン × グループ単位（`:291-303`、`:515-517`）。
- prefill は `KvarnStoredKElement`/`KvarnStoredVElement`（`kvarn_read_device.hpp:173-219`）を要素ごとに呼ぶ（`attention_tile.hip:233-235,325-327`、`attention_wmma.hip:700-705`、`attention_batched.hip:74-120`）。各要素は `KvarnRawDecodedElement`（`kvarn_read_device.hpp:94-103`）でスカラー展開する。
- 書き込みは `FusedQKNormRoPEKvWriteKernel`（`fused.hip:21`）と `BatchedFusedQKNormRoPEKvWriteKernel`（`prefill_rope.hip:18`）が、KVarN 選択時に `KvarnFwhtRowShared`（`kvarn_device.hpp:19-37`）で回転して sink/tail/チャンク平面へ F16 行を書く。密な FP16 経路は `k_cache_f16`/`v_cache_f16` の行へ書く（`fused.hip:189-235`、`prefill_rope.hip:153-160,221-260`）。封印は `kvarn_seal.hip`（128 × 256、KV ヘッドごとに 1 ブロック）。
- 状態は KVarN コンパクトスナップショット `GQKVSNP1`・版 3・128 バイトヘッダ（`arena.cpp:23-59`）と、永続 payload `kQwenPersistentPayloadVersion=3`（`inference_backend.cpp:130-136`）。同一性は `QwenCompatibilityIdentity`（`inference_backend.cpp:318-360`）が `state_abi`（`QwenStateAbiName`）・`kv_storage`・`numerics=` などのタグから作り、ビルド ID を含まない。したがって演算を変えたビルドの区別は、タグか `state_abi` の更新で行う必要がある。KVarN の `state_abi` は 2026-10-04 の保管先修正で 1 世代上げた前例がある（`qwen-gfx1151-state-v5-` / `qwen-gfx1151-dflash-state-v6-`）。
- 品質ハーネスは `tests/models/qwen/hip/quality/kvarn_quality_eval.cpp`（`EXCLUDE_FROM_ALL`、`tests/models/qwen/CMakeLists.txt:90-96`）が (format, tail, corpus, depth) 単位の JSON を書き、位置配列 `kl`/`nll_teacher`/`nll_candidate` を持つが位置ごとの argmax ID を持たない（`:664-729`）。`tools/qwen27b/kvarn_quality.py` は corpus/run/status/wait/report を提供し、基準線が同じラベルに無い場合は `--anchors-label` で別ラベルから注入する（`:565-585`）。ゲート定数は品質優先 0.15・メモリ優先 1.0（`:222-234`）。
- 試験用値の前例: 前回変更のタスク 2.4/2.5 が `GUFO_QWEN_PSEUDO_KVARN` と `baseline-q8`/`baseline-q4` を gpu-test 専用で導入し、タスク 3.10 が削除した（Phase 0 の `pseudo-kvarn-*` 経路も同時に削除され、git に残っていない）。`tests/cli/kv_cache_test.py` の `REMOVED_PROBES`（`:31-36`、`:174-185`）が現在の拒否を固定している。

### 記録済みの数値

- 品質: G0 の k6v5 L2048 最悪 p 0.143（128K 大逸脱率、暫定）。T-08 は 4K/32K のみ・アンカー方式で最悪 p 0.087、32K は D14 除外で 4 窓（`QUALITY.md:125-170`）。2026-10-09 のマージ後の再測定（G0 の窓、アンカー方式）は 32K 平均 KL p 0.202（窓 2）・128K 0.154 を記録し、利用者が未達のまま受理した（`openspec/changes/archive/2026-10-09-merge-upstream-main/tasks.md` のタスク 5.4）。この再測定では q8/q4 基準線の値が前後で完全に一致し、教師 logits の SHA-256 も一致したので、変化は候補側にある。生の平均 KL は 32K で 0.07043 → 0.13225、128K で 0.10306 → 0.11131 に上がり、1〜2 位置の大きな KL スパイク（c0/32768 の位置 2 +9.8、c1/32768 の位置 52 +25.5、c2/32768 の位置 1 +9.7）が平均を押し上げていた。アンカーは Phase 0 の試験経路のビルドで測ったもので、変化には fork 自身の本番経路への移行が含まれ、原因は未確定（同タスクの原因調査）。
- 速度: G1 基準値（k6v5 L2048 の FP16 比）は tg 0.996 / 0.979 / 0.854 / 0.631、pp 0.985 / 0.920 / 0.891 / 0.830（深度 0 / 4K / 32K / 128K、`BENCHMARKS.md:179-197`）。128K の読み出しの深度コスト（tg のトークン時間の深度 128K と深度 0 の差）は 131.6 ms（`EXPERIMENTS.md:109`）、キャッシュ常駐の計算のみの見積りは約 122 ms 対 FP16 34 ms（`:110`）。過去の共有 KV 試作は 74→107 VGPR・LDS +16 KiB・占有率 12→5 wave/CU で不採用（`:105`）、8 キーブロックは 111 VGPR・約 2 wave/SIMD で退行（`:107`）。キーごと処理（`kKeyBlock=1`）が最良（`:109`）。pp は系列間で最大 2.4%、tg は 0.2% 以下ずれる（前回変更の D19）。
- ハーネスの所要: 128K の 1 窓 ≈10 分（`docs/models/qwen3.8-27b/PREUSE-REPORT.md:75-76`）、4K+32K の 8 コーパス ≈28 分。一致性スイートの 128K は 1 単位 ≈510 秒、32K は ≈135 秒（同）。

### 制約

- 既定は `fp16`。production に環境変数スイッチや試験用経路を残さない。1 挙動 = 1 正規ロングオプション。FP16 の保持バイト列・同一性キー・スナップショット互換は不変。KVarN の出力のビルド間一致は契約に含まない。
- 測定は 1 本ずつ・見積もり 1 時間以内・見積もりの 2 倍で自動停止・`tools/qwen27b/ledger_run.py` 経由（前回変更の D16/D22/D23/D26 を継続）。チャット形式の生成は `reasoning_effort: low`。

## Goals / Non-Goals

**Goals:**

- 基準線 E_q8 / E_q4 を gpu-test 専用の実行可能な構成として復元し、候補と同一の窓・位置で測る。
- k6v5 L2048 の p ≤ 0.13 を全深度・全 4 指標で確定する（努力目標 0.10 は記録のみ）。k4v4 L256 の p ≤ 1 を同じ窓で再確認する。128K は判定用の新規窓で再判定する。
- タイル単位の読み出しスパイクを二段階で go/no-go 判定し、go の場合は共通ウォーカーへの作り直しで 8K / 128K の FP16 比を改善する。
- 速度を落とさない品質改善を実装する。32K の prefill 直後のスパイクの原因を切り分ける。
- 形式・演算を変更した場合の版と同一性キーの規則を実装する。

**Non-Goals:**

- 既定の昇格、FP16 経路の変更、production への baseline 値の露出。
- 既存の速度の下限・退行規則・p99 / C8 / 起動時間の本変更での判定（記録のみ。再測定と適用は後続の変更）。
- 適合テール長以外のテール長の再評価（G0 の値を据え置く）。
- 統計的なタスク評価、画像文脈、層別ビット割当、スケール類の FP32 化。

## Decisions

### D1. 基準線は gpu-test 専用の書き込み時量子化で復元する

- `CMakeLists.txt` にコンパイル定義オプション（前回と同じ `GUFO_QWEN_PSEUDO_KVARN`、既定 OFF）を再追加し、`CMakePresets.json` の `gpu-test` だけで ON にする。release・cpu プリセットには含めない。
- 有効時は `--kv-cache` に `baseline-q8`・`baseline-q4` を登録する（`src/cli/kv_cache_options.hpp` の `KvCacheValueList`/`ValidateKvCacheSelection` と `src/models/qwen/hip/execution_policy.hpp` の `ResolveQwenKvCache`）。release では既存の「未知の値」経路がそのまま拒否する。`tests/cli/kv_cache_test.py` の `REMOVED_PROBES` は「gpu-test では受理、release では拒否」に更新する。
- 基準線は専用のストレージ種別として扱い、ポリシーの `Fingerprint()` と互換同一性キーに含める（FP16 や KVarN の状態と相互再利用しない）。テールを持たず、`--kv-cache-tail` との併用は起動時エラーにする。
- 書き込み時に sink（絶対位置 0〜127）以外の各行へ「回転（`KvarnFwhtRowShared` による H·x）→ ブロック 32 の q8_0 / q4_0 量子化（FP16 スケール）→ 逆量子化 → 逆回転（Hᵀ）」を適用し、既存の FP16 平面へ格納する。H は直交なので注意の結果は回転領域で量子化した場合と等価になり、読み出し経路は変更しない（Q も回転しない）。フックは密な FP16 経路（K は RoPE 後に行が揃う位置、V は行の完成時）に置く。
- 基準線の回転は正規化 Hadamard 行列（符号パターンなし）に固定する。基準線と教師は Phase 0 で 1 回だけ測って最終判定まで再利用するので、D7 で KVarN 側の回転を変えても基準線は変えない。
- G0 の窓（教師はキャッシュ済み）の 4K で E_q8 / E_q4 を測り、G0 の値との差を `QUALITY.md` に記録する。差は合否の条件にしない（同一窓・同一実装の基準線で判定するため、G0 との差は判定に影響しない）。差の要因として「回転領域の量子化結果を逆回転して FP16 に格納するときの追加の丸め」を仮説として挙げ、実測の差と並べて記録する。この丸めの大きさ（q8 の誤差の 1/8 程度という見積り）は未検証である。
- 代替案: 読み出し側で量子化する案は本番読み出し経路に試験用分岐が残るため採らない。回転したまま格納して Q も回転する案は、FP16 経路の読み出しに回転を持ち込むため採らない。アンカー方式（前回変更 D-27）は基準線の窓と実装が候補と異なるため本変更でやめる。

### D2. p は同一ラベルの基準線で計算し、位置ごとの top-1 を記録する。窓は深度ごとに分ける

- `kvarn_quality_eval.cpp` の単位 JSON に位置ごとの `top1_match` と `argmax` ID（候補・基準線）を追加する。既存の集計 `top1_agreement` は位置配列から導出して整合させる。
- 基準線は候補と同じ `run`（同じコーパス・深度・窓）の候補として渡す（例: `--candidates baseline-q8,baseline-q4,kvarn-k6v5,kvarn-k5v4,kvarn-k4v4`）。`report` は同一ラベル内の基準線で p を計算し、`--anchors-*` は本変更の判定に使わない。
- ゲート定数を更新する: 品質優先予算 0.13（全深度・全 4 指標）、努力目標 0.10 は記録のみ（合否に使わない）、メモリ優先 1.0 は据え置き。`report --gate` の終了コードは、k6v5 の 0.13 と k4v4 の 1.0 の判定に従う。
- 窓:
  - 4K: `t08-reduced` の 8 窓を再利用する。
  - 32K: `t08-reduced` にコーパスを追加し、D14 の除外後 6 窓以上にする。
  - 128K（開発用）: G0 のコーパス 0〜2 の窓（`g0-tail` の教師を、重みとトークン列の SHA-256 の一致を確認して再利用する）。原因調査と改善策の確認はここで行う。
  - 128K（判定用）: 新しいシードのコーパスを D14 の除外を見込んで多めに用意し、除外後 6 窓以上にする。本測定まで教師と基準線以外は測らない。
- 4K / 32K は判定にも改善の確認にも同じ窓を使う。許容位置との余裕が大きい（T-08 で最悪 0.087）ためで、余裕の小さい 128K だけを分ける。
- 128K は 1 単位を 5 窓以内に分割する（1 窓 ≈10 分）。教師を先に流して除外を確定してから基準線と候補を測る。
- 許容位置 0.13 と 0.10 は測定前に固定し、結果を見て変更しない。
- 代替案: 全深度で開発用と判定用の窓を分ける案は、最も偏りが少ないが、4K / 32K の教師と基準線の測定が数時間増える。分けない案は費用が最小だが、0.13 を T-08 の結果を見た後に決めたことと、改善策を同じ窓で選ぶことによる偏りが、余裕の小さい 128K に残る。

### D3. 判定と未達時の扱い

- 判定する候補は、品質優先 `kvarn-k6v5` L2048（p ≤ 0.13）とメモリ優先 `kvarn-k4v4` L256（p ≤ 1）。`kvarn-k5v4` L2048 は記録のみで、4K / 32K と 128K の開発用の窓で測る。
- 適合テール長は G0 の 4 通りの評価で確定した値を据え置き、他のテール長は再評価しない。
- 最終判定は候補だけを測る（基準線と教師は Phase 0 で 1 回測って再利用する）。
- k6v5 のいずれかの深度・指標で p > 0.13 の場合、または k4v4 で p > 1 の場合は、bpv が増える改善（例: メタデータの FP32 化、約 +0.06 bpv）の採用または目標の見直しを利用者に返す。許容位置は動かさない。
- 代替案: k6v5 だけを判定する案は、読み出しと量子化の変更が全プリセットの数値を変えるのに、余裕の小さいメモリ優先（G0 の最悪 0.971）の契約を確かめないことになる。4 通りのテール長をすべて測り直す案は、128K だけで数時間増え、本変更の目的（k6v5 L2048 の確定）に比べて費用が大きい。

### D4. 速度スパイク（一次判定）

- `tools/qwen27b/kvarn_read_compute_bench.hip` を拡張し、タイル単位の試作を追加する。1 ワークグループが（KV ヘッド, split）を担当し、GQA の 6 クエリヘッドをまとめて処理する。タイル（128 キー）ごとにコードをマジックナンバー法で f16 に変換し、スコアはレーンごとにキーを受け持つ方式（`v_dot2_f32_f16`）または WMMA、最大値・`exp`・再スケールはタイル単位、V は 6 ヘッドで展開を共有して蓄積する。
- ビルドは `tools/bench/build.sh` の hipcc 経路（`kvarn_reference.cpp` をリンク。ファイル冒頭のレシピ）を使い、VGPR/SGPR/LDS と占有率を取得する。
- 正しさを CPU 参照で確認した上で、同じベンチ内で現行カーネルと FP16 も動かし、(a) キャッシュ常駐の直接時間（既存の 4 点フィットの外挿ではなく 8K 文脈を直接）と、(b) 128K 相当のストリーミング（16 層分のワーキングセットを持ち回るか、同等の退避トラフィックになるようループする）の両方で比較する。
- 一次判定: 同じベンチの (b) で、試作の読み出し時間が現行カーネルの 0.5 倍以下で、spill や占有率の崩れがないこと（前回の共有 KV 試作は 12→5 wave/CU に落ちた）。満たさなければ速度の作業をここで止め、`EXPERIMENTS.md` に不採用として記録する。
- 二次判定は D5 の最初の手順で、本番の経路で行う。
- 代替案: 単体ベンチだけで最終判断する案は、実カーネルの占有率・同期・メタデータ配置の効果を測れないため採らず、一次判定の足切りに限る。最初から本番の経路に組む案は、見込みのない試作にも仮組みの費用がかかるため採らない。単体ベンチの時間を本番の深度コスト 131.6 ms と直接比べる案は、測り方が違う量の比較になるため採らない。

### D5. 読み出しの共通ウォーカー（一次判定が go の場合）

- 最初の手順（二次判定）: 試作を本番の起動経路に仮組みし、`gufo bench` で `kvarn-k6v5` L2048 の深度 0 と 128K の tg を同じ系列で測る。深度コスト（tg のトークン時間の深度 128K と深度 0 の差）が 131.6 ms の 0.5 倍以下（65.8 ms 以下）であれば作り直しを続け、満たさなければ仮組みを削除して速度の作業を止め、`EXPERIMENTS.md` に記録する。
- `kvarn_read.hip` の `KvarnWalkPartition` をタイル単位の共通ウォーカーに置き換え、online・split-K・因果検証が同じヘルパーを同じ順序で使う。T-05 のビット一致は構造で保つ。sink とテールリングの F16 チャンクも同じ構造で読む。
- 因果検証のキー 1 個ごとの `__syncthreads`（`kCausalChunk = kKeyBlock = 1`）と要素ごとの `KvarnUnpackCode` をなくし、タイル単位で（行数 × 6 ヘッド）分をまとめて展開する。
- prefill（`attention_tile.hip`、`attention_wmma.hip`、`attention_batched.hip`）の要素ごとの `KvarnStoredKElement`/`KvarnStoredVElement` を、タイル単位のベクトル展開（メタデータはタイルごとに 1 回）に置き換える。WMMA の有界ワークスペース逆量子化は維持する。
- 封印カーネル（`kvarn_seal.hip`）は 8K / 128K の pp のプロファイルで効いている場合だけ手を入れる。FP16 経路と封印の中身は変更しない。
- 演算順序が変わるため、KVarN の greedy 出力は旧ビルドと一致しなくなりうる（FP16 の契約は不変）。経路間一致（T-05）、スナップショット往復は必須の回帰とする。
- DFlash2 と AR の一致は、短い文脈の `qwen_dflash_gpu_test` に加えて、`tools/qwen27b/kvarn_consistency.py` を `kvarn-k6v5` L2048 で縮小実行して確かめる。32K で 4 単位以上（1 本、≈135 秒/単位）、128K で 3 単位以上（1 本、≈510 秒/単位）とし、封印境界を最初の検証窓に含む単位を選ぶ（128K の配置は `tools/qwen27b/probe_kvarn_128k.py`）。
- 作り直しの後、8K / 128K を D8 の方法で測り、変更前（Phase 0 の基準点）の 0.97 倍以上であることを確かめてから採用する。
- 代替案: 経路ごとに別々に最適化する案は、online・split-K・検証の演算順序がずれて T-05 のビット一致を失いやすい。prefill を変えずに decode だけ作り直す案は、128K の pp（0.830）が改善しない。深い文脈の一致を 4.4 と同じ規模（299 単位）で測り直す案は十数時間かかり、1 時間の制限で分割しても費用に見合わない。

### D6. 形式・演算の変更と版

- ペイロードの配置または量子化演算（回転・正規化・RTN）を変えた場合は、`kKvarnCompactSnapshotVersion` と `state_abi`（`QwenStateAbiName` の KVarN 側の世代）を上げる。永続 payload に影響する場合は `kQwenPersistentPayloadVersion` も追随させる。
- 読み出し経路（decode・検証行・prefill）の演算の順序または算術だけを変えた場合も、`state_abi` を上げる。同一性キーはビルド ID を含まないので、上げなければ旧ビルドの KVarN ディスクキャッシュが同じキーで再利用され、復元後の生成がコールド実行と一致しなくなる（「キャッシュ機構との状態契約」に反する）。ペイロードの形式は変わらないので、コンパクトスナップショットの版は上げない。
- どれも変更しない場合は形式・版・同一性キーを変更しない。FP16 のスナップショット・バイト列・同一性キーは常に不変。
- この判断は go/no-go に関係なく、Phase 2 と Phase 3 が終わった後に一度だけ行う（Phase 3 の量子化の変更も対象に含めるため）。
- 代替案: 同一性キーに `kvarn_read=` のような新しいタグ行を足す案は、FP16 のキー文字列も変わってしまうか、KVarN だけ行を出し分ける分岐が必要になる。`state_abi` の KVarN 側の世代を上げる方式は既存の前例（2026-10-04 の保管先修正）と同じで、FP16 の文字列に触れない。

### D7. 品質改善の選定（速度を落とさないもの）

- Phase 1a（128K）: 128K の開発用の窓の高 d 位置について、教師実行のダンプ（gpu-test のダンプオプション）から一部層の FP16 K/V タイルとクエリを書き出し、CPU オラクル（`src/models/qwen/kvarn_reference.cpp` の `KvarnNormalizeTile`、`KvarnQuantizeAsymmetricRtn`、`KvarnFwhtHeadInPlace`）で次を比較する: 現行、FP32 メタデータ、K の平均を引く、固定の符号パターンを掛けた Hadamard、雑音のバイアス補正（タイルごとに `−½·scale²·token_scale²·Σq'²/12`）、q8_0、k8。スコア誤差、量子化領域への注意質量、コピー元重みの変化を求めて改善策を順位付けする。長い GPU 実行は行わない。
- Phase 1a（32K のスパイク）: G0 の窓の 32K で prefill 直後の位置（c0 の位置 2、c2 の位置 1 など）に出ているスパイクを切り分ける。Phase 0 の試験経路のコードは削除済みで git に残っていないので、(1) `g0-tail` の位置ごとの KL（Phase 0 の試験経路の成果物）とマージ後の本番経路の成果物（`merge-upstream-quality`）を同じ窓・同じ位置で対応づけて差の大きい位置を特定し（オフライン）、(2) 短い GPU 実行（1 時間以内、台帳経由）で、その位置について本番経路の prefill チャンク幅（256 と 4096）と、前置文脈の末尾を逐次 decode で通した場合を比べる。prefill から decode への切り替え境界の不具合か、量子化誤差かを判定する。不具合であれば原因と修正方針を記録し、Phase 3 の改善候補に加える。
- Phase 3: 上位の改善を共通ヘルパーへ実装する。採否は、8K / 128K の tg と pp の FP16 比を変更前の 0.97 倍以上に保つかどうか（D8）で判定する。キーあたりの命令数による事前の制約は置かない（バイアス補正のようにトークンスケールを使う補正は、キーごとに演算が 1 回増えうるため）。回転の変種（固定の符号パターンを掛けた Hadamard）を採る場合は、書き込み側の回転・注意出力の逆回転・CPU オラクル・回転のテスト（`qwen_kvarn_fwht_cpu_test`、`qwen_attention_fusion_ops_test`）を同じ回転にそろえる。基準線の回転は変えない（D1）。bpv が増える案は採用前に利用者の確認を得る。
- 簡易確認は 4K / 32K（約 28 分）と 128K の開発用の窓で行う。128K の判定用の窓は使わない。
- 代替案: キーあたりの命令数の上限を数値で定める案は、ISA を数える手間が増えるうえ、最終的な基準である速度の測定と二重になる。原因調査を 128K だけに絞る案は、32K も必達の対象で、本番経路の境界の不具合である可能性を残す。

### D8. 速度の記録、非劣化、既存契約の繰り延べ

- 8K / 128K は `tools/qwen27b/g1.py run --depths 8192,131072 --configs k6v5-t2048` を 3 系列実行し、公表済みの方法（pp は 3 系列の中央値、tg は同じ系列、FP16 を各系列で測定）で FP16 比を記録する。系列ごとに新しい `--out` ディレクトリを使う（`.done` マーカーで完了点を再開する）。
- 測る時点: Phase 0（変更前の基準点）、Phase 2 の後（go の場合）、Phase 3 の後、Phase 4（最終）。各変更は、その直前の測定値（no-go の場合の Phase 3 は Phase 0 の値）の 0.97 倍以上を tg と pp の各点で保つことを採用の条件とする。0.97 は D19 の退行規則と同じ幅で、pp の系列間のずれ（最大 2.4%）を吸収する。
- 既存の速度の下限（深度 0〜4K の AR tg ≥ 0.95 など）、深度 32K 以上と pp の基準値 0.97 倍規則、p99 / p50、C8、起動時間は本変更では判定しない（利用者の決定、2026-10-09）。再測定と適用は後続の変更で行い、そのことを `BENCHMARKS.md` と README に記録する。
- 代替案: 許容幅ゼロ（変更前の値以上）は、中立な変更でも pp のノイズで不採用になる。各点の系列間のばらつきを許容幅にする案は、測定ごとに幅が変わり、事前に固定できない。

### D9. 実行と記録の方法

- 前回変更の D16 / D22 / D23 / D26 を継続する: 切り離し実行、単位ごとの成果物と再開、1 本ずつの実行、見積もり 1 時間以内、見積もりの 2 倍で自動停止、`ledger_run.py` で IN / PROGRESS / OUT を `artifacts/test-ledger.jsonl` に記録。
- 128K の品質単位と一致性スイートの単位は 1 時間以内に分割し、各単位の見積もりと根拠を台帳に書く。
- 速度測定中は他の GPU ジョブを同時に実行しない。
- 代替案: 複数のテストを 1 本の連続実行にまとめる案は、前回変更で止まったテストが GPU を 25 時間占有した経緯（D22/D23）から採らない。

## Risks / Trade-offs

- [128K は 1 位置で p が約 0.03 動く] → 判定用の窓を除外後 6 以上にし、窓単位ブートストラップ 95% 区間を併記する。点推定だけで結論を急がない。
- [スパイクが一次または二次判定に届かない] → 速度の作業を止め、`EXPERIMENTS.md` に不採用として記録する。品質の作業は現行カーネルの上で続ける。
- [タイル共有で占有率が崩れる（前回の 12→5 wave/CU、107〜111 VGPR）] → 最初から VGPR / LDS / 占有率を測り、spill が出たらタイル幅・ヘッド共有数・ステージングを先に見直す。
- [基準線復元の FP16 丸めで G0 の値とずれる] → G0 の窓の 4K で差を測って `QUALITY.md` に記録する。判定は同一窓・同一実装の基準線で行うので、差は合否に影響しない。
- [32K の窓が D14 除外で 4 しかない] → コーパスを追加して除外後 6 窓以上を確保する。追加窓でも除外が起きうるので多めに用意する。
- [アンカー方式の値が基準線の窓と実装に依存する] → 同一窓の基準線に切り替え、区間を併記する。旧アンカーの記録は残す。
- [32K のスパイクの原因が本番経路の不具合である] → Phase 1a で成果物の対応づけと短い GPU 実行で切り分け、不具合なら Phase 3 で修正する。Phase 0 の試験経路は残っていないため、比較は保存済みの位置ごとの KL に限られる。
- [4K / 32K は判定と改善の確認に同じ窓を使う] → 余裕が大きい（T-08 の最悪 0.087）ことを根拠に受け入れ、128K だけ判定用の窓を分ける。
- [p ≤ 0.13 または k4v4 の p ≤ 1 に届かない] → bpv が増える改善の採用または目標の見直しを利用者に返す。許容位置を動かさない。
- [読み出し変更で KVarN の出力が変わる] → T-05、経路間一致、深い文脈での DFlash2 と AR の一致、スナップショット往復で確認する。KVarN の出力のビルド間一致は契約でない。
- [読み出しの演算だけの変更で旧キャッシュが再利用される] → D6 により `state_abi` を上げ、旧キャッシュは再計算させる。
- [版を上げると旧 KVarN の状態が読めない] → 利用開始前で実利用の状態は無い（既定 `fp16`）。FP16 の互換は不変。古い KVarN キャッシュは同一性キーで分離され再計算される。
- [長時間のハーネス（128K ≈10 分/窓）と判定用の窓の追加] → 5 窓以内の単位に分割し、単位ごとに成果物を残して再開する（D9）。判定用の窓は教師と基準線を Phase 0 で 1 回、候補を最終判定で 1 回だけ測る。
- [マージ後のアンカー再測定のように、測定経路の変更が候補側の数値を動かす] → 同一ラベルで基準線と候補を測り、ユニット単位のハッシュと教師 logits の同一性を確認してから比較する。

## Migration Plan

1. Phase 0（評価基盤）: 基準線の復元と検証（V-01）、ハーネス拡張（V-02）、窓の準備（V-03）、基準線と現行候補の測定（V-04）、速度基準点（V-05）。
2. Phase 1a（原因調査、V-06）と Phase 1b（速度スパイクの一次判定、V-07）。一次判定が no-go の場合は Phase 2 を省略し、Phase 3 以降を現行カーネルの上で行う。
3. Phase 2（一次判定が go の場合のみ）: 二次判定（V-13）。no-go なら仮組みを削除して Phase 3 へ。go なら読み出しの作り直しと回帰確認、深い文脈での一致（V-14）、8K / 128K の非劣化（V-08）。
4. Phase 3（V-09）: 品質改善の実装と簡易確認、8K / 128K の非劣化。
5. 版と同一性キーの確定（V-12）: go/no-go に関係なく、Phase 2 と Phase 3 の変更を踏まえて一度だけ行う。
6. Phase 4（V-10、V-11）: 最終品質判定、8K / 128K の速度記録、文書更新（`QUALITY.md`、`BENCHMARKS.md`、`EXPERIMENTS.md`、`README.md`、`docs/CLI.md`）。

ロールバック: 既定は `fp16` のため、`--kv-cache` を指定しない限り挙動は変わらない。KVarN 経路に問題が出た場合はオプションを外すだけで旧経路に戻る。FP16 の同一性キーとスナップショットは変更しないため、既存の `.kvc` はそのまま再利用される。
