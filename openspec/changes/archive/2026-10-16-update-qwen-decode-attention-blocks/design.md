# Design

## Context

### 共通

- この変更の対象は Qwen3.8 27B（`src/models/qwen`）だけである。Qwen3.8 Flash-Next（`src/models/qwen38_flash_next`）には同じ考え方を別の変更 `update-qwen38-flash-next-decode-attention-blocks` で適用し、採否・ゲート・時期を独立に扱う（利用者の決定、2026-10-13）。カーネル・テスト・ベンチ・数値契約はモデル間で共有しない（`AGENTS.md`）。共有するのは「KV ヘッドごとにクエリヘッドを WMMA の M 次元へまとめ、K・V のタイルを 1 回だけ LDS に置いて共有する」という設計の考え方だけとする。
- production は gfx1151 + HIP のみ。Triton/AOTriton/CK/MIOpen を依存に加えない。1 挙動 1 正規ロングオプション（エイリアス禁止）。production に環境変数スイッチや試験用の経路を残さず、不採用の経路は削除する。
- 測定は `tools/bench/build.sh`（standalone HIP、`nix develop -c tools/bench/build.sh [name]`）と `tools/prof/prof.py`（`run` / `show` / `diff`、rocprofv3 のカーネル別集計、`--pass N` で計測パスに限定）を使う。
- 先行計画 `openspec/changes/update-qwen27b-block-decode-attention` は存在しない。`openspec/changes/` 配下、全ブランチ（`git log --all`）、作業ツリーとホームディレクトリを検索して確認した。
- この変更は gufo_bt の現行ブランチ（`kvarn-kv-cache-quantization`、作成時の先頭 `801abd3`）で確認した。KVarN の読み出しは本ブランチの成果物である。`main`・`origin/main`（`f783fed`）と `upstream/main`（`f37fb01`）は KVarN のコミットを含まない。

### Qwen3.8 27B

- 形状: フル注意 16 層、クエリ 24・KV 4（GQA 6）、head_dim 256（`tests/models/qwen/hip/attention/kv_storage_ops_test.cpp:47-59`、`src/core/model_config.hpp:40-48`。KVarN 側の形状制限は `src/models/qwen/hip/execution_policy.hpp:213-220`）。
- 現行の decode は系列長で経路が決まる。128 未満はオンライン、128 以上は split-K（分割数 32、パーティション長 `ceil(n / 32)`）。`src/models/qwen/hip/detail/attention_policy.hpp:16-17,53-59`、`src/models/qwen/hip/kernels/attention_decode.hip:553-557,661-665`。
- FP16 の split-K は、系列長 512 以上では 1 ブロックが 1 つの（KV ヘッド, 行, split）を受け持ち、6 クエリヘッドで 4 トークンの K/V を LDS に置いて共有する（`attention_decode.hip:868-887,735-760`）。ただし各ヘッドは、キーごとのレーン間縮約、`expf` 2 回の再スケール、値の蓄積を別々に行う（同 `676-733`）。系列長 128 以上 512 未満は 1 ブロック = 1 クエリヘッドである。値の蓄積は `fmaf` と `__fmul_rn` で固定されている（同 `723-731`）が、スコアの内積は通常の `*` と `+` で書かれており（同 `686-707`）、明示的な `fmaf` では固定されていない。現行の grid は `dim3(num_kv_heads, rows, 32)` で、系列長 512 なら 4 × 32 = 128 ブロックを起動する（gfx1151 は 40 CU）。
- 共有されている部品: `SelectDecodeAttentionSplitCount`（`attention_policy.hpp:53-59`）は FP32 と FP16 の split-K（`attention_decode.hip:920-934`）と KVarN の読み出し（`kvarn_read.hip:1153`）が使う。`QwenDecodeSplitKAttentionReduceKernel`（`attention_decode.hip:789` 以降）は FP32 と FP16 の split-K が使い、`+=` と `*` で書かれている。KVarN は独自の統合 `QwenKvarnSplitKReduceKernel` を持つ。
- KVarN の split-K は、すでに 128 トークンのタイル境界に整列している（変更 `add-kvarn-kv-cache-quantization` の design D8）。タイル数 `blocks = ceil(n / 128)` を 32 個のパーティションに `⌊s·blocks/32⌋` で均等に配り（`src/models/qwen/hip/kernels/kvarn_read.hip:661-671`）、検証行は 1 回の起動の中で行ごとに分割を決め（同 `829` 以降）、キーを持たないパーティションは統合で読み飛ばす（同 `703-704`）。現行の KVarN の検証は、行を 1 つのカーネルの LDS ステージで共有して T-05 のビット一致を保っている（`attention_decode.hip:993-1003`）。
- 帯域と計算の現状（Q8_0、`docs/models/qwen3.8-27b/BENCHMARKS.md:283-291`）: FP16 の同じキーの読み出しは 9.0 ms（32K）・35.7 ms（128K、約 240 GB/s、1 トークンで 8.6 GB）。KV を常駐させた計算だけの時間は FP16 で 33.9 ms（128K、16 フル注意層の 1 トークン、層あたり約 2.1 ms。`docs/models/qwen3.8-27b/EXPERIMENTS.md:110` の計算だけの測定では 34 ms）。両者はほぼ同時に限界に近い。
- resident の測り方: 128K の FP16 KV は 1 層 512 MiB で、SoC のキャッシュに収まらない（`EXPERIMENTS.md:135`）。先行ツール `tools/qwen27b/kvarn_read_compute_bench.hip` は、1 層分の KV が常駐する文脈（2304〜9216 トークン）を掃引し、（クエリヘッド, キー）あたりの単位コストを最小二乗で当てはめて 128K に換算している（同ファイル `1-11`、`EXPERIMENTS.md:110`）。
- 効果が見込める 2 か所: (a) DFlash2 の検証（制御器の実測表 `kQ4ContextCost = {0.11, 0.14, 0.21, 0.23, 0.25, 0.31, 0.35}` は 2K→32K の追加コストを約 100 ms のサイクルに対する相対値で持ち、1 行が 0.11、8 行が 0.35。`src/models/qwen/dflash_policy.hpp:300-306`。Q8 DFlash2 mixed の C1 の 128K は 8.87 対 11.62 tok/s で −23.7%。`BENCHMARKS.md:73-80`）。(b) KVarN（decode はキーごとの展開で計算律速。常駐時の計算だけで `kvarn-k4v4` 53.9 ms・`kvarn-k6v5` 121.5 ms に対し FP16 33.9 ms。`kvarn-k5v4` テール 2048 の AR は 128K で FP16 比 0.752。`BENCHMARKS.md:206-214,283-291`）。
- DFlash2 制御器の文脈コスト表の使われ方: Q8 ターゲットの単一リクエストは `1.0F + 0.02F * length` を使い、表を参照しない（`dflash_policy.hpp:109-113`）。表は Q4 ターゲットの判断と、Q8 ターゲットの 4 リクエストと複数リクエストのコホートの判断（同 `160-215`）に使われる。表の出典は Q4 の C1 の offline estimate（`docs/models/qwen3.8-27b/artifacts/q4-dflash2-c1-focused.json` の `controller_cost_calibration`）である。
- 契約: `long_context_ops_test` は FP64 参照に対し 5e-4（`tests/models/qwen/hip/attention/long_context_ops_test.cpp:139-198`）。`kv_storage_ops_test` は検証行とスカラー decode の byte 一致を `memcmp` で要求し、開始位置 {0, 17, 120, 124, 127, 128, 504, 508, 511, 512, 8192, 32768, 65536} と作業領域の 2 種の容量を検査する（`kv_storage_ops_test.cpp:84-118`）。`docs/models/qwen3.8-27b/QUALITY.md:1-16` は AR/DFlash2 の一致と検証幅 2〜8 の全 logits の一致を記録している。`QUALITY.md` の再現は `tools/qwen27b/check.py` の各スイートで行う（`QUALITY.md:397-405`）。
- 互換同一性: `QwenCompatibilityIdentity`（`src/cli/serve/inference_backend.cpp:358-397`）は、`numerics`、`prefill_attention`、`attention_split_min_context`、`attention_split_count`、`kv_storage` などを含む。decode 注意の分割はすでに再利用の互換条件として扱われている。`qwen/kv-cache-quantization` の「セッション状態の整合」は、FP16 の同一性キーが同じコミットの upstream のビルドとバイト一致することを求め、「KV ストレージ形式の選択」は FP16 の挙動と保持バイト列の不変を求めている。dense FP16 平面を使う構成（`UsesFp16AttentionKv()`、gpu-test の基準線 `baseline-q8` / `baseline-q4` を含む）は FP16 の decode の注意を通る。
- MTP は FP32 と FP16 の両平面を渡し、FP32 平面が非 null のため FP32 の split-K に入る（`src/models/qwen/hip/mtp/executor.cpp:100-106,226-230`、`attention_decode.hip:922-926`）。MTP の予測器の入力は対象モデルの隠れ状態なので、FP16 の decode が変わると MTP の出力は変わりうるが、MTP 自身の注意の算術は変わらない。
- HIP グラフは split-K を必要とする decode を捕捉しない（`execution_policy.hpp:360-397` の `kSplitKAttentionRequired`）。グラフ経路はオンラインのカーネルだけを使う。
- 却下済みの先行実験（`EXPERIMENTS.md`）:
  - 104: `kvarn_read.hip` の `#pragma clang fp contract(off)` は、収縮を有効にすると機械結合器が別の積部分集合を融合して T-05 のビット一致が壊れるため維持されている。
  - 105: KVarN の decode で封印タイルを KV ヘッドごとに 1 回だけ LDS へステージする案は byte 一致だが、VGPR が 74→107、共有メモリ +16 KiB で占有が 12→5 ウェーブ/CU になり、d32K の AR tg が 6.73→6.54 で戻された。
  - 107: KVarN の読み出しで K/V の算術を折り込み、明示的な `fmaf` と 8 キーのブロックにした案は byte 一致だが、VGPR が 111 になり、全ての長い深度で遅かった。
  - 135・139: 変更 `improve-kvarn-k6v5-quality-and-speed` のタイル単位の試作（KV ヘッド × split ごとに 1 ワークグループ、GQA 6 ヘッドで f16 に展開したタイルを LDS で共有、タイル単位の max/exp/再スケール。WMMA は使っていない）は、57 SGPR・64 VGPR・spill 0・占有率 10 wave/SIMD と資源は健全だったが、128K 相当のストリーミングで現行の 1.3846 倍（8.5534 ms 対 11.8427 ms）と遅く、不採用になった。キャッシュ常駐では `kvarn-k6v5` で 0.87 倍と勝ったが、`kvarn-k4v4` では 1.70 倍で負けた。低ビットでは計算量が減り、タイル展開の LDS トラフィックが律速になった。
- KVarN の品質本測定 T-08（変更 `add-kvarn-kv-cache-quantization` の tasks 6.1）は完了している。評価窓の各位置は `ForwardToken`（R=1 の decode）で計算されるため（`tests/models/qwen/hip/quality/kvarn_quality_eval.cpp:363-379`）、T-08 は decode の読み出しを検査する。FP16 の教師も decode で作られるので、Phase 1 の後は教師がビルドごとに変わる。`QUALITY.md:282` 以降の p は G0 の窓の基準線で求めた値であり、変更 `improve-kvarn-k6v5-quality-and-speed` 後の品質契約は異なる窓の基準線の流用を禁じている。
- `qwen/kv-cache-quantization` の性能契約は、深度 32K 以上の AR と DFlash2 の tg と全深度の pp を、最初の判定で記録した FP16 比（基準値）の 0.97 倍以上で判定する。FP16 の decode の注意を置き換えると、tg の比の分母が変わる。pp は prefill の注意（この変更の対象外）で決まるため、分母は変わらない見込みである。
- 繰り延べた判定: 変更 `improve-kvarn-k6v5-quality-and-speed` は、深度 0〜4K の AR の tg の下限、深度 32K 以上の tg と全深度の pp の基準値からの退行、深度 0 の DFlash2 の下限、p99 / p50、C8 の合計スループット、起動時間の判定を、後続の変更へ繰り延べた。`kvarn-k6v5` テール 2048 の 128K の pp は G1 基準値の 0.947 倍で、未判定のまま記録されている（`BENCHMARKS.md:178-194`、`docs/models/qwen3.8-27b/README.md:98`）。

## Goals / Non-Goals

**Goals:**

- 27B の decode・検証の注意を、KV ヘッドごとのブロックでクエリヘッドを WMMA の M 次元へまとめ、K・V のタイルを 1 回だけ LDS に置く構造にする。
- 行の独立性とビット一致の契約を保ったまま、DFlash2 の検証コストを下げる。
- KVarN の読み出しを同じ考え方の構造へ移し、読み出し量の削減が速度に効くようにする。
- 採否を Phase 1（FP16）と Phase 2（KVarN）で判定し、不採用の段階には変更を残さない。

**Non-Goals:**

- prefill の注意（tile / WMMA / batched）、系列長 128 未満のオンライン経路、HIP グラフ経路、FP32 参照 KV 経路、GEMM 試験経路、KVarN の封印とスナップショット形式。
- Qwen3.8 Flash-Next（別の変更で扱う）。Flash-Next の互換同一性も変えない。
- 切り替えのオプション、環境変数、段階的な併用（採用したら旧カーネルを削除する）。
- 許容誤差やビット一致の契約の緩和。
- 基点より前のビルドと upstream のビルドで作った FP16 のディスクキャッシュの再利用（D19 で互換同一性を変える）。

## Decisions

### 共通

#### D1. ブロックの受け持ちと WMMA の M 次元、タイルの共有

1 ブロックが 1 つの（KV ヘッド, 行, パーティション）を受け持ち、その KV ヘッドを共有するクエリヘッド（GQA 群）を WMMA の M 次元に並べる。K・V のタイル（128 トークン）は 1 回だけ LDS に置き、GQA 群のヘッドで共有する。モデルごとのヘッド数と KVarN の扱いは、各モデルの節で決める（27B は D14）。

代替案: 現行の構造（KV を LDS で共有しても、ヘッドごとにキー単位の縮約と再スケールをする）を維持する方式は、ヘッド方向の重複した縮約と再スケールを残すため、この変更の目的が達成できない。FP16 で行を M 次元へ混ぜる方式は、行ごとに因果の終端が違うため、タイルの範囲と行の独立性の扱いが複雑になる。LDS へステージするだけで WMMA を使わない方式は、KVarN で既に試して戻されている（`EXPERIMENTS.md:105,135`）。本設計はさらにヘッド方向の縮約の重複を WMMA で消す点が異なる。

#### D2. Q と P を f16 の上位と残差に分けて積和する

WMMA の入力は f16（仮数 11 bit）であるため、A 側（Q と P）をそれぞれ f16 の上位とその残差の 2 成分に分け、FP32 累算の WMMA で足し合わせる。B 側（FP16 の K・V、KVarN の量子化コード）は f16 で正確に表せる見込みなので、積は A 側の上位と残差の 2 つで足りる。相対誤差は 2⁻²² 程度を見込み、FP32 に近い精度を目標にする。残差は値が小さいと f16 の非正規化数の範囲に入り精度が落ちるため、Phase 0 の精度測定に小さな値を含める（Risks）。分けない版（上位のみ）は単体ベンチで速度の参考として測るだけにし、本番のコードには含めない。

代替案: bf16 は仮数が 8 bit で精度が足りない。tf32/f32 の WMMA は gfx1151 の対象命令に無く、エミュレーションは命令数で不利になる。FP32 のまま縮約する方式は現行と同じ計算律速を残す。分けない f16 のみの方式は、精度が基点のカーネル以下であることを示せない限り採れない（D5）。

#### D3. 行の独立性、算術順序の固定、WMMA の外の明示的な `fmaf`

各行の結果は、同じ起動の他の行の値と行数 R に依存させない。検証行とスカラー decode のビット一致を保つため、head_dim 方向の分担、タイルの分割、WMMA の累算順序（フラグメントの順序とタイルの順序）、縮約の木を R によらず同じにする。WMMA の外のスカラーの積和（オンライン softmax の再スケール、部分注意の統合、タイルごとの後処理）は明示的な `fmaf` に固定する。基点のスコアの内積は `fmaf` で固定されていないが、ビット一致の契約は新しいカーネルの行どうし（検証行とスカラー decode）の間のものであり、基点のカーネルとの一致は求めない。

複数の行が 1 ブロックで展開済みのタイルを共有する場合（27B の KVarN、D14）も、各行は自分の系列長 n で決まるパーティションのタイルだけを、R=1 と同じ手順で処理する。タイルの展開は行に依存しない決定的な処理とし、行ごとの WMMA、タイル内の n 以降のキーの除外、タイルの順序、統合を R=1 と同じにする。ブロックは、そのパーティション番号について全行が必要とするタイルの和集合を展開し、各行は自分の範囲のタイルだけを読む。

根拠: KVarN では `#pragma clang fp contract(off)` を外すと機械結合器が別の積部分集合を融合し、検証行のビット一致が壊れた（`EXPERIMENTS.md:104`）。つまり「同じ式を書く」だけでは一致しない。WMMA の累算は FP32 だが和の順序はタイル分割に依存するため、行数・タイル数によらず同じ順序を選ぶ必要がある。

#### D4. 旧カーネルの削除と切り替えの不存在

採用した段階では、置き換えた旧カーネルを削除し、切り替えのオプションと環境変数を残さない。Phase 1 では FP16 の split-K の部分注意カーネル（`QwenDecodeSplitKAttentionHalfPartialsKernel`）、Phase 2 では KVarN の split-K の部分注意カーネルと因果 decode の読み出しカーネルを削除する。FP32 参照 KV の経路が使う `QwenDecodeSplitKAttentionPartialsKernel` と `QwenDecodeSplitKAttentionReduceKernel` は残す。不採用の段階では旧カーネルを維持する。

代替案: 一方を選べるように残す方式は「不採用の経路は削除する」という方針に反し、2 つの経路のビット一致を永久に保守する負荷を生む。

#### D5. 精度は FP64 参照との最大絶対誤差と RMS 誤差で基点以下を要求する

同じ入力について、FP64 の参照に対する最大絶対誤差と RMS 誤差が、基点のカーネルの値以下であることを採否の条件にする。比較は R=1 で、系列長 128、129、4096、4097（タイル境界と方式 A のパーティション長が変わる境界）、32768、131072（G0F の速度の点）で行う（利用者の決定、2026-10-13）。入力は、`long_context_ops_test.cpp` と同じ生成式の入力（飽和しない入力）と、P と Q の残差が f16 の非正規化数の範囲に入る小さな値を含む入力の 2 種とする。KVarN は主構成 `kvarn-k5v4` テール 2048 で、封印済みの値から計算した FP64 参照に対して同じ比較をする。既存の許容誤差（5e-4）は緩めない。分けない版の誤差も記録するが、判定には使わない。

代替案: 相対誤差のみで判定する方式は、値が小さい要素の誤差を見逃す。FP32 との差で判定する方式は、FP32 自体が参照にならない（基点の FP16 経路はすでに FP32 の縮約と一致しない）。入力を新しく設計する方式は、既存テストの入力との比較ができなくなる。

#### D6. 測定は Phase 0 の単体ベンチと本番の 2 段

Phase 0 は単体ベンチで、基点のカーネルを逐語コピーした対照と比べて cold と resident の両方を測り、5 回以上の中央値を取る。FP64 の参照と、飽和しない入力を用意する。resident は先行ツール（`tools/qwen27b/kvarn_read_compute_bench.hip`、`EXPERIMENTS.md:110`）と同じく、1 層分の KV が常駐する文脈（2304〜9216 トークン）を掃引し、（クエリヘッド, キー）あたりの単位コストを最小二乗で当てはめて深度 128K に換算した値とする。本番は `BENCHMARKS.md` と同じ方法で、同じ測定系列の基点のビルドと交互に測る。比較はリクエスト・フェーズごとの時間で行い、差が 5% と 3 ms の両方を超える場合を有意な差とし、リクエスト間で平均しない（`AGENTS.md`）。

代替案: いきなり本番の HTTP 測定だけで判定する方式は、深度と R の組合せごとに分離できず、原因の切り分けができない。対照を置かない方式は、機械差と実装差を区別できない。128K を文字どおり常駐させる方式は、1 層 512 MiB がキャッシュに収まらないため成り立たない。`main` または `upstream/main` を対照にする方式は、KVarN を含まず、基点との間に無関係な差分があるため採らない。

#### D7. GPU を使う測定は重ねない

GPU を使う測定は、他の GPU ジョブや、変更 `update-qwen38-flash-next-decode-attention-blocks` の測定と時間を重ねない。

根拠: 変更 `add-kvarn-kv-cache-quantization` の G1 では、測定条件の揺れ（ツールチェーンと流用した分母）が判定を難しくした（`openspec/changes/archive/2026-10-08-add-kvarn-kv-cache-quantization/design.md` D18）。

代替案: 繰り返し回数を増やして揺れを統計的に吸収する方式は、時間の重なりによる系統的な偏りを除けず、測定時間も延びるため採らない。

#### D8. 採否は段階ごとに決め、不採用の段階の要求はアーカイブ前に外す

Phase 1（FP16）と Phase 2（KVarN）をそれぞれ判定する。Phase 1 が不採用なら Phase 2 には進まず、D9 に従う（G0K の基準が FP16 の新しいカーネルであるため）。

Phase 1 を採用し Phase 2 を採用しない場合は、アーカイブ前に次を行う。

- `qwen/decode-attention` の仕様差分から、次の要求を外す。
  - 「KVarN 読み出しの同じ構造への移行」
  - 「KVarN 読み出しの折り込みと状態 ABI」
  - 「単体ベンチのゲート（KVarN）」
  - 「本番のゲート（KVarN）」
  - 「繰り延べた判定の適用」
  - 「KVarN の品質の非退行」
- 次の記述から KVarN の部分を外す。
  - Purpose の「と KVarN の decode コスト」
  - 「精度の非劣化」の KVarN の文
  - 「旧カーネルの削除」の Phase 2 の文と Scenario
  - 「結果の記録と未達時の扱い」の「状態 ABI の更新」の記録（KVarN の FP16 比の記録は G1R の結果として残す）
- `qwen/kv-cache-quantization` の MODIFIED（FP16 の互換同一性と tg の基準値の測り直し）は残す。

Phase 1 も採用しない場合は、すべての仕様差分を外して `.openspec.yaml` に `skip_specs: true` を設定し（デルタの無い変更は `--strict` の検証で拒否されるため）、測定の記録だけを残す。いずれも `openspec validate --strict` を通してからアーカイブする。

代替案: 不採用の段階の要求を残したままアーカイブする方式は、実装に無い挙動を spec に残し、後続の変更を誤らせるため採らない。段階ごとに change を分ける方式は、G0K と G1R が Phase 1 の成果に依存するため、change の間の順序の管理が増える。

#### D9. ゲート未達時は利用者に判断を仰ぐ

単体ベンチまたは本番のゲートに届かない時点、または原因の分析で見込みがなくなった時点で作業を止め、測定値、原因の分析、考えられる選択肢を利用者に返す。利用者の判断なしに基準の変更、予定外の最適化の継続、変更の中止を行わない。

根拠: 変更 `add-kvarn-kv-cache-quantization` の D18（`.../2026-10-08-add-kvarn-kv-cache-quantization/design.md`）の未達時の扱い。

代替案: 閾値の近くで届かない場合に最適化を続ける方式は、測定前に閾値を固定した意味を失うため採らない。未達の段階を自動的に不採用として次へ進む方式は、原因の分析と選択肢を利用者が見ないまま範囲を決めることになるため採らない。

#### D10. WMMA フラグメントへの詰め方は実装時に決める

GQA 群のヘッド数が WMMA の 16 行の M 次元に満たない場合、無効行をゼロで埋めるか、行を分割して WMMA を 2 回にするかは実装時に決める。どちらも精度と行の独立性の契約には影響せず、速度だけに影響する。モデルごとの値は各モデルの節に書く。

### Qwen3.8 27B

#### D11. パーティションの方式は Phase 0 で A と B を測って選ぶ

パーティションの不変条件（境界は 128 の倍数、数は 32 以下、各行の n だけから決める）を満たす 2 つの方式を、Phase 0 の単体ベンチで両方測り、事前に決めた基準で選ぶ（利用者の決定、2026-10-13）。

- A: パーティション長 `L = round_up(ceil(n / 32), 128)`、数 `ceil(n / L)`。行どうしで L が違う場合（n が 4096 の倍数をまたぐ場合）は行を群に分けて起動する。n ≤ 4096 では L = 128 で、n = 4097 では 17 パーティション（最後は 1 トークン）になる。
- B: KVarN の既存方式。タイル数 `blocks = ceil(n / 128)` を 32 個のパーティションに `⌊s·blocks/32⌋` で配り、行ごとにカーネル内で決める。群に分けた起動は要らない。n < 4096 ではキーを持たないパーティションが生じ、統合で読み飛ばす。n = 4097 では 32 パーティション（1 つが 2 タイル）になる。

どちらの方式も、FP16 の新しい経路専用の関数として `attention_policy.hpp` に置き、FP32 と KVarN が使う `SelectDecodeAttentionSplitCount` は変えない（D12）。

選択の基準（G0P）: 両方が精度（D5）と独立性（G0F の独立性の項目）を満たすことを前提に、G0F の速度の点（R=1 と R=8、深度 32K と 128K、cold、5 回以上の中央値）で比べる。一方がどの点でも他方より 5% を超えて遅くならず、少なくとも 1 点で 5% を超えて速ければ、その方式を採る。差がすべて 5% 以内なら B を採る（既存の KVarN と同じ方式で、群に分けた起動が要らない）。点によって勝ち負けが分かれた場合は D9 に従う。片方だけが精度と独立性を満たす場合はその方式を採り、どちらも満たさない場合は D9 に従う。5% は本番の有意差の幅（D6）に合わせた。選んだ方式は Phase 2 の KVarN にも使う（A を選んだ場合、KVarN の分割も変わるが、Phase 2 ではどのみち状態 ABI を上げる）。

代替案: 基点の `ceil(n / 32)` の均等分割は、128 トークンの WMMA タイルが 2 つのパーティションにまたがり、部分タイルの読み出しとスケール適用が二重になる。パーティション長を定数にする方式は、深い文脈で分割数が 32 を超える。

#### D12. 変更しない経路と、共有部品の分離

系列長 128 未満のオンライン経路、HIP グラフ経路、FP32 参照 KV 経路、prefill の注意（tile / WMMA / batched）、GEMM 試験経路は変えない。MTP の予測器の注意は FP32 平面を渡すため FP32 参照経路に入り、変わらない（実装時に `mtp/executor.cpp` を再確認する）。split-K の作業領域が与えられない場合のオンライン経路への退避（`attention_decode.hip` の `LaunchAttention` の分岐）も変えない。

FP16 の新しい経路は、専用のパーティション関数と専用の統合カーネルを持つ。FP32 参照 KV の経路が使う `SelectDecodeAttentionSplitCount` と `QwenDecodeSplitKAttentionReduceKernel`、KVarN が使う `SelectDecodeAttentionSplitCount` と `QwenKvarnSplitKReduceKernel` は、Phase 1 では変えない。

これらの経路が変わっていないことは、ダンプで確かめる（G0U）。ダンプは、公開の起動関数だけを使って固定の入力の出力をファイルに書き出す standalone HIP のツールとする。対象は次の 3 つ。

- 系列長 127 のオンライン経路
- MTP と同じ引数の FP32 参照 KV の経路（系列長 128・4096・32768）
- KVarN の decode と検証行（`kvarn_read_compute_bench.hip` と同じく CPU の参照エンコーダで封印した固定入力）

同じソースを基点と候補のソースツリーでそれぞれビルドして実行し、出力を `cmp` で比べる。

代替案: グラフ経路も同じ構造にする方式は、グラフが split-K を捕捉できず（`QwenGraphRejection::kSplitKAttentionRequired`）、捕捉できない経路を増やすとグラフの適格性が落ちる。オンライン経路も変える方式は、浅い文脈のビット一致の根拠を失う。共有の分割関数と統合カーネルを変える方式は、FP32（MTP）と KVarN の算術を Phase 1 で変えてしまい、「変更しない経路」と D17 の前提（KVarN の読み出しを変えていない状態での基準値の測り直し）が崩れる。既存の演算テストの合格だけで「変わっていない」とする方式は、宣言限界内の一致しか示せず、バイト一致を示せない。

#### D13. 27B の狙いは DFlash2 の検証と KVarN に絞る

FP16 の AR decode は 128K で読み出し 35.7 ms と常駐時の計算 33.9 ms が同時に限界に近く、どちらも削らない限り速くならない。この変更が削るのはヘッド方向の重複計算なので、AR が速くなることは見込まない。狙いは (a) DFlash2 の検証（8 行の追加コストが約 100 ms のサイクルの 0.35、`dflash_policy.hpp:300-306`）と (b) KVarN の decode（常駐時の計算だけで 53.9 ms / 121.5 ms、`BENCHMARKS.md:283-291`）に絞る。したがって FP16 の単体ベンチのゲートは「検証が 0.5 倍以下」と「AR の退行なし（cold 1.03 倍以下）」の組合せにする。27B の GQA 群は 6 ヘッドで、WMMA の M 次元（16）に満たない（D10）。

代替案: AR の tg の下限をゲートにする方式は、帯域律速の経路に達成不能な条件を課す。

#### D14. KVarN の読み出しを同じ考え方の構造へ移す（Phase 2）

KVarN の decode と検証の読み出しは、1 ブロックが 1 つの（KV ヘッド, パーティション）を受け持ち、その起動の全行を処理する（利用者の決定、2026-10-13）。

- 封印タイルは 1 ブロックにつき 1 回だけ展開して LDS に置き、6 ヘッドと全行で共有する。
- WMMA は行ごとに回し、6 ヘッドを M 次元に並べる。各行の算術が R に依存しないための規則は D3 に従う。
- spec の「KV ヘッドごとのブロック」（FP16 の（KV ヘッド, 行, パーティション））とはブロックの受け持ちが異なり、KVarN の構造は「KVarN 読み出しの同じ構造への移行」で別に定める。
- KVarN の折り込み（チャネルスケール・ゼロ点のクエリ側への集約、トークンスケールのスコアへの乗算、V の正規化空間での蓄積とタイル単位のチャネルスケール適用）は、WMMA の A 側と、タイルごとの FP32 の後処理に割り当てる。
- 逆量子化テンソルはグローバルメモリへ実体化しない。
- 読み出しの算術が変わるため状態 ABI（`inference_backend.cpp` の `QwenStateAbiName`）を上げ、旧キャッシュを無効化する。FP16 の互換同一性は Phase 2 では変えない。

根拠と先行実験との関係:

- 不採用になった先行実験
  - 「封印タイルを KV ヘッドごとに 1 回だけ LDS へステージする」案（`EXPERIMENTS.md:105`）は、占有が 12→5 ウェーブ/CU に落ちて戻された。
  - 「K/V の算術の折り込みと明示的な `fmaf`、8 キーのブロック」の案（`EXPERIMENTS.md:107`）は、VGPR 111 で遅く戻された。
  - 変更 `improve-kvarn-k6v5-quality-and-speed` のタイル単位の試作（`EXPERIMENTS.md:135,139`）は資源が健全なまま、128K 相当で現行の 1.38 倍と遅かった。f16 へのタイル展開の LDS トラフィックが律速になり、`kvarn-k4v4` の常駐では 1.70 倍だった。
- 本設計が異なる点
  - 6 ヘッド分のスコア・縮約・値の蓄積を WMMA にまとめ、ヘッドごとのスカラーの縮約と再スケールを無くす（135 の試作は WMMA を使っていない）。
  - 展開を検証行の間でも共有し、R=8 の展開を 1 回にする（135 の試作は行ごとに展開した）。
- 残る危険: タイル展開の LDS トラフィックが律速になる危険は残る。G0K で VGPR 数、占有、LDS の転送量またはタイル展開の時間を記録し、届かない場合は D9 に従う。

代替案: キーごとの現行読み出しを維持する方式は、計算だけでも 128K で 53.9 ms あり、FP16 の 33.9 ms を下回らない。封印タイルを FP16 ワークスペースへ逆量子化して既存の FP16 注意へ渡す方式は、読み出し量の削減が失われ、常駐時に不利になる。FP16 と同じく（KV ヘッド, 行, パーティション）で行ごとに展開する方式は、R=8 で展開が 8 回になり、G0K の R=8 の 0.5 倍の見込みが弱まる（利用者の決定、2026-10-13）。

#### D15. 単体ベンチのゲートの閾値と評価点（確定値）

閾値と評価点は確定値とする（利用者の決定、2026-10-13）。測定の前に固定し、結果を見て変更しない。

- G0F
  - 精度（D5）
  - 独立性: R ∈ {1, 2, 3, 8}、開始位置は `kv_storage_ops_test` の集合と 4093・4095・4096・4097・131064 で、各行が byte 一致
  - 計算の下限: R=1、深度 128K の resident（D6 の換算値）の 1 層分の時間が 0.72 ms 以下
    - 0.72 ms は、`kvarn-k5v4` テール 2048 の総量 5.08 bpv で 1 層分約 170 MB を、FP16 の深度増分から得た実測帯域約 240 GB/s で読む時間
    - 基点は層あたり約 2.1 ms
  - 検証: R=8 の cold の時間が、深度 32K と 128K で基点の 0.5 倍以下
  - AR の退行なし: R=1 の cold の時間が、深度 32K と 128K で基点の 1.03 倍以下
  - 記録のみ（判定に使わない）: 深度 128・512・4096 の R=1 の cold の時間（Risks の浅い深度の並列度）
- G0K（主構成 `kvarn-k5v4` テール 2048）
  - 精度と独立性
  - R=1 の cold の時間: FP16 の新カーネルに対して、深度 128K で 0.50 倍以下、深度 32K で 0.70 倍以下
  - R=8 の cold の時間: 深度 32K と 128K で、基点の KVarN の検証読み出しの 0.5 倍以下

根拠: 0.5 倍は「ヘッド方向の重複除去で検証コストが半分になる」という設計の狙い、1.03 倍は「AR が悪化しない」ことの判定、0.72 ms は「FP16 の計算が KVarN の読み出し時間に隠れる」ための上限、KVarN の 0.50/0.70 倍は読み出し量が FP16 の 1/3 前後（`kvarn-k5v4` テール 2048 の 5.08 bpv）になることに対応する。240 GB/s は変更 `add-kvarn-kv-cache-quantization` の design D18 で、FP16 の 128K の増分 35.8 ms と 1 トークンの KV 8.59 GB から得た実測値である。評価点を深度 32K と 128K の cold と主構成に揃えたのは、閾値の根拠がこの点で書かれているためである。浅い深度の退行は G1F の C1 の AR と C8 で見る。

代替案: 深度 128・512・4K の R=1 もゲートにする方式は、浅い深度の並列度の低下を単体ベンチで捕まえられるが、注意がトークン時間に占める割合が小さい点で止まる見込みが上がる。G0K を全プリセットで判定する方式は、常駐時の計算がプリセット間で 2.3 倍違い、閾値の根拠（5.08 bpv）と合わない。

#### D16. 本番のゲート（G1F / G1K）

比較の基準は、同じ測定系列で基点のビルドと交互に測った値とする。有意な差は、リクエスト・フェーズごとの時間の差が 5% と 3 ms の両方を超える場合とする（利用者の決定、2026-10-13。`AGENTS.md` の規則）。

- G1F（FP16、Q8_0 の重み。利用者の決定、2026-10-13）
  - 品質: `tools/qwen27b/check.py` の `kernels`・`model`・`multi-session`・`serving` に通る。`tests/functional/run.py` の `long-context` と `cache` に、AR と DFlash2 の各モードで通る。
    - `cache` は、D19 で互換同一性を変えるため加える。
    - `check.py reference` は BF16 の参照モデルが要り、FP16 の decode の変更の検査に寄与しないため含めない。
  - C1 の AR: tg と pp に、`BENCHMARKS.md` の単一利用者の全深度で、有意な退行が無い。
  - C8 の AR と DFlash2: `BENCHMARKS.md` の複数利用者の方法（利用者あたり文脈 4096、tg128）で、有意な退行が無い。
  - C1 の DFlash2: tg が深度 32K・64K・128K で有意に改善する。
  - 文脈コスト表の更新: DFlash2 は `kQ4ContextCost` を新しいカーネルで測り直して制御器を更新したビルドで測る。Q8 の C1 の制御器は表を使わない（`dflash_policy.hpp:109-113`）ため、C1 の DFlash2 の改善は検証の注意の速さだけで決まる。表の更新は、Q8 の C8 のコホートの草案長に効く。
- G1K（KVarN）: 次をすべて満たす（利用者の決定、2026-10-13）。
  - T-01〜T-05 に通る。
  - `qwen/kv-cache-quantization` の性能契約の下限
    - すべてのプリセットについてテール長未指定と 2048 で、深度 0〜4K の AR の tg が FP16 比 0.95 倍以上、深度 0 の DFlash2 の tg が 0.95 倍以上。
    - 主構成 `kvarn-k5v4` テール 2048 の C8 AR の合計スループットが FP16 比 0.95 倍以上、起動時間の悪化が 5% 以下。
    - 主構成と `kvarn-k6v5` テール 2048 の p99 / p50 が FP16 の 1.05 倍以下。
  - 同じ性能契約の基準値に対し、FP16 比が 0.97 倍以上。
    - 深度 32K 以上の AR と DFlash2 の tg は、Phase 1 を採用した場合は D17 で測り直した値を基準値にする。
    - 全深度の pp は、既存の基準値を使う。
  - 上の 2 項目で、変更 `improve-kvarn-k6v5-quality-and-speed` が繰り延べた判定を KVarN の読み出しを移したビルドに適用し、その旨を記録する（利用者の決定、2026-10-13）。
  - `kvarn-k5v4` テール 2048 の T-08
    - 深度 4K と 32K の `t08-reduced` の評価窓で、基点と候補のそれぞれについて、同じビルドで作った教師と同じ窓の基準線 E_q8 / E_q4 を用いて p を求める。
    - 深度ごとに、平均 KL・中央値 KL・大逸脱率・top-1 不一致率のすべてで、候補の p から基点の p を引いた値が 0.05 以下であること（改善は制限しない。利用者の決定、2026-10-13）。
    - p が定義できない深度・指標（E_q4 ≤ E_q8）は、既存の品質契約と同じく判定不能として報告し、未達とする。
  - 新しい FP16 比を、プリセット・テール長・深度ごとに記録し直す。

根拠:

- 基点を同じ系列で交互に測ると、ツールチェーンと履歴の違いを分母から除ける（D7）。
- T-08 は R=1 の decode を通るため、Phase 2 の読み出しを直接検査する。ただし `QUALITY.md:282` 以降の p は G0 の窓の基準線で求めた値で、現行の品質契約では流用できない。そのため基点でも同じ手順で測り直す。
- p は同じビルドでは決定的に同じ値になるが、算術がわずかに変わると位置ごとの大逸脱の判定が入れ替わる。変更 `add-kvarn-kv-cache-quantization` の G0 では、1 位置で p が約 0.029 動いた（同 design D17）。0.05 は、その 1〜2 位置分の揺れを許す幅である。

代替案:

- G1F を Q8_0 の C1 だけで判定する方式は、新カーネルを通る複数セッションの退行を見ない。
- Q4 と Q8 の `QUALITY.md` の表すべてで判定する方式は、測定が数倍になる。
- Q8 の C1 の制御器に文脈コストを入れる方式は、制御器の変更というスコープの拡大になり、受理率と草案長の別の検証が要る。

#### D17. KVarN の tg の基準値の測り直し（G1R）

Phase 1 を採用したビルドで（KVarN の読み出しはまだ変えていない状態）、性能契約の基準値の点のうち、FP16 の分母が変わる深度 32K 以上の AR と DFlash2 の tg を測り直す（すべてのプリセット、テール長未指定と 2048）。同じ手法で FP16 KV と交互に測り、新しい基準値として、置き換え前の基準値と並べて `BENCHMARKS.md` に記録する。

- pp の基準値は据え置く。pp は prefill の注意で決まり、この変更で分母が変わらないためである。
- この扱いは、`qwen/kv-cache-quantization` の性能契約を MODIFIED で改める（利用者の決定、2026-10-13）。
- Phase 1 を採用しない場合は測り直さない。

代替案:

- 既存の基準値を据え置く方式は、FP16 の DFlash2 が速くなるほど KVarN の FP16 比が下がり、KVarN を変えていないのに退行と判定される。
- pp も含めて全点を測り直す方式は、分母が変わらない点の基準値を変える理由が無い。また、繰り延べた未判定の退行（`kvarn-k6v5` テール 2048 の 128K の pp が G1 基準値の 0.947 倍）を、判定しないまま新しい基準値に取り込む。
- 判定を後続の変更へ繰り延べる方式は、読み出しを変える Phase 2 を基準なしで採用することになる。

#### D18. 27B の順序

1. Phase 0: 単体ベンチの対照と候補（分割方式 A・B）と、変更しない経路のダンプを用意し、G0P で分割方式を選び、G0F を判定する。
2. Phase 1: 次の順で進める。
   1. 本番のカーネルを、専用の分割関数と統合カーネルで実装する。
   2. G0U で、変更しない経路が基点とバイト一致することを確かめる。
   3. G1I として FP16 の互換同一性に項目を加える。
   4. 本番のカーネルで G0F を再確認する。
   5. `kQ4ContextCost` を測り直して制御器を更新する。
   6. G1F を判定する。採用したら旧カーネルを削除し、G1R で KVarN の tg の基準値を測り直す。
3. Phase 2: KVarN の単体ベンチの対照と候補を用意して G0K を判定し、本番の読み出しを移して状態 ABI を上げ、旧カーネルを削除し、G1K を判定する。

T-08 の完了は待ち条件にしない（アーカイブ済みの T-08 で満たされている。利用者の決定、2026-10-13）。GPU を使う測定は D7 に従う。

代替案:

- Phase 1 と Phase 2 を同時に作る方式は採らない。G0K の基準（FP16 の新カーネル）と D17 の基準値の測り直しが、Phase 1 の確定を前提にしているためである。
- 互換同一性の更新を G1F の後に回す方式は採らない。G1F の `cache` のスイートが更新後の挙動を検査できなくなるためである。

#### D19. FP16 の互換同一性に decode 注意の算術を表す項目を加える

Phase 1 で FP16 の decode と検証行の注意の算術が変わるため、`QwenCompatibilityIdentity`（`inference_backend.cpp:358-397`）に、FP16 の decode 注意の算術を表す行（例: `fp16_decode_attention=kv-head-wmma-v1`）を加える。

- 対象は dense FP16 平面を使う構成（`UsesFp16AttentionKv()` が真。gpu-test の基準線を含む）だけとする。FP32 と KVarN の互換同一性には加えない。
- 行の値は、FP16 の decode と検証行の注意の算術を変えるたびに変える。
- FP16 のスナップショットの版と形式、`state_abi` の文字列、Flash-Next の互換同一性は変えない。
- これに合わせて、`qwen/kv-cache-quantization` の「KV ストレージ形式の選択」と「セッション状態の整合」を MODIFIED で改める（利用者の決定、2026-10-13）。
- 基点より前のビルドと upstream のビルドで作った FP16 のディスクキャッシュは再利用されず、再計算になる。正しさは保たれるため BREAKING としない（利用者の決定、2026-10-13）。

根拠: 生成済みの応答を含むキャッシュは、decode で書いた KV と再帰状態を保存する。旧い decode の算術で作った状態を新しい算術のビルドで再利用すると、キャッシュを使わない同じ条件の実行とトークン列が一致しなくなりうる。既存の互換同一性は decode 注意の分割（`attention_split_*`）を項目に持っており、算術の変更も互換同一性で表すのが既存の設計に合う。

代替案:

- `numerics` の値を変える方式は、FP32 と KVarN の互換同一性も変える。KVarN の同一性キーは「読み出し経路の演算を変更しない場合は同じ」でなければならない（「KVarN の形式・演算の変更と版の更新」）ため、採らない。
- FP16 の `state_abi` の文字列を変える方式は、状態の配置ではなく算術の違いを表すことになり、既存の項目の意味とずれる。
- 互換同一性を変えない方式は、旧い算術の FP16 キャッシュの再利用を許す。

## Risks / Trade-offs

### 共通

- [LDS とレジスタの増加で占有が落ち、速度が伸びない] → 1 ブロックあたりの LDS は「1 タイル + GQA 群のクエリと出力」に抑える。R=1 と R=8 の両方を測り（G0F）、VGPR 数と占有を記録する。届かない場合は D9 に従う。
- [f16 の上位・残差の分割で精度が基点に届かない] → D5 の FP64 比較を Phase 0 の最初に置く。小さな P や Q の残差が f16 の非正規化数の範囲に入る入力を含める。届かない場合は、A 側をタイル単位で 2 のべきに正規化してから分割する案を比べ、それでも届かなければ D9 に従う。
- [WMMA の累算順序が R やタイル幅で変わり、ビット一致が壊れる] → D3 のとおり順序を固定し、R ∈ {1, 2, 3, 8} と開始位置の境界集合で byte 一致を検査する。

### Qwen3.8 27B

- [KVarN でも占有とレジスタの問題が再発する] → KVarN では同種の案が占有 12→5（`EXPERIMENTS.md:105`）と VGPR 111（`EXPERIMENTS.md:107`）で戻されている。G0K で VGPR 数と占有を記録する。
- [KVarN のタイル展開の LDS トラフィックが律速になる] → タイル単位の試作は資源が健全なまま 128K 相当で 1.38 倍と遅く、`kvarn-k4v4` の常駐では 1.70 倍だった（`EXPERIMENTS.md:135,139`）。G0K で LDS の転送量またはタイル展開の時間を記録し、展開を全行で 1 回にする（D14）。届かない場合は D9 に従う。
- [浅い深度で並列度が落ちる] → 境界を 128 の倍数に揃えると、系列長 4096 未満ではキーを持つパーティションが ceil(n/128) 個以下になり、ブロック数が基点より減る（例: n=512 で基点 4 × 32 = 128 ブロック、新方式 4 × 4 = 16 ブロック）。G0F で深度 128・512・4096 の R=1 の時間を記録し、退行は G1F の C1 の AR と C8 の AR・DFlash2（利用者あたり文脈 4096）で判定する。影響は未測定である。
- [FP16 の AR がこの変更で速くならない（狙いの外）] → D13 のとおり狙いを DFlash2 と KVarN に置き、AR には退行なしの条件だけを課す。
- [DFlash2 の有意な改善に届かない] → 検証の追加コストは 8 行で約 100 ms の 0.35（`dflash_policy.hpp:300-306`）なので、検証コストを半分にできれば深い文脈で届く見込み。Q8 の C1 の制御器は文脈コスト表を使わないため、草案長は変わらず、改善は検証の注意の速さだけで決まる。届かない場合は D9 に従う。
- [KVarN の読み出しの再構成で T-05 のビット一致が壊れる] → WMMA の外の `fmaf` の明示と算術順序の固定を維持し、行を共有する場合も D3 の規則に従う。`qwen_attention_kvarn_read_ops_test` の T-03・T-05 と、R ∈ {1, 2, 3, 8} の行の独立性を新しい構造で通す。状態 ABI を上げて旧キャッシュを無効化する。
- [FP16 の互換同一性の更新で、利用者の既存の FP16 キャッシュが使えなくなる] → 不一致として明示的に再計算され、正しさは保たれる（D19）。`docs/models/qwen3.8-27b/README.md` と `docs/CLI.md` に記録する。
- [KVarN の状態 ABI の更新で、利用者の既存の KVarN キャッシュが使えなくなる] → KVarN は不一致として明示的に再計算される。`docs/models/qwen3.8-27b/README.md` と `docs/CLI.md` に記録する。
- [Phase 1 で FP16 が速くなり、KVarN の FP16 比が下がる] → D17 で tg の基準値を測り直し、Phase 2 はその基準値で判定する。
- [繰り延べた判定で G1K が未達になる] → `kvarn-k6v5` テール 2048 の 128K の pp は G1 基準値の 0.947 倍で記録されており、既存の基準値で判定すると 0.97 倍を下回る見込みがある。その場合は D9 に従い、測定値と原因の分析を利用者に返す。
- [G1K の測定が長い（全プリセット × テール長の性能契約と T-08）] → 変更 `add-kvarn-kv-cache-quantization` の D16・D22 と同じく、数分を超える測定は切り離したプロセスで起動し、見積もりと進捗を台帳に記録する。T-08 の教師はビルドごとに作り直す。
- [MTP が影響を受ける] → MTP の予測器の注意は FP32 平面を渡すため FP32 参照経路に入る（`mtp/executor.cpp:226-230`）。実装時に再確認し、G0U のダンプで FP32 経路のバイト一致を確かめ、`qwen_mtp_gpu_test` を動かす。MTP の入力となる対象モデルの隠れ状態は FP16 の decode の変化で変わりうる。

## Migration Plan

1. Phase 0: `tools/bench/` の standalone HIP に、基点のカーネルの逐語コピーの対照と、ブロック構造の候補（分割方式 A・B）と、変更しない経路のダンプを置き、G0P と G0F を判定する。未達なら D9 に従う。
2. Phase 1（FP16）: 本番のカーネルを専用の分割関数と統合カーネルで実装し、G0U、G1I、G0F の再確認を行い、`kQ4ContextCost` を測り直して G1F を判定する。採用なら旧カーネルを削除し、G1R で KVarN の tg の基準値を測り直す。不採用なら D8・D9 に従う。
3. Phase 2（KVarN）: 単体ベンチで G0K を判定し、読み出しを同じ考え方の構造へ移し、状態 ABI を上げ、旧カーネルを削除し、G1K を判定する。
4. 文書: 次を記録する。
   - 記録先: `docs/models/qwen3.8-27b/{BENCHMARKS,EXPERIMENTS,QUALITY,README}.md` と `docs/CLI.md`
   - 内容: 採用可否、測定値、不採用の理由、tg の基準値の測り直し、FP16 の互換同一性の更新と、キャッシュの再計算
5. 不採用の段階の仕様差分を外し（D8）、`openspec validate --strict` を通してからアーカイブする。

ロールバック:

- 採用の判定までは、基点の旧カーネルが既定で、ビルド単位で元に戻せる。
- Phase 1 を採用したビルドと基点のビルドは FP16 の互換同一性が異なるため、互いの FP16 のディスクキャッシュを再利用せず再計算になる（正しさは保たれる）。
- KVarN で読み出しの算術を変えた後は状態 ABI が上がり、旧キャッシュは再利用されず再計算になる。
- FP16 のスナップショットの版と形式、FP32 の互換同一性は、どの段階でも変わらない。
