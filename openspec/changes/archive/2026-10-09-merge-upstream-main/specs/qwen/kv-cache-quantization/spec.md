# Spec Delta

## ADDED Requirements

### Requirement: キャッシュ機構との状態契約

システムは、RAM プレフィックスキャッシュ、実行中プレフィックスの共有、学習した境界、安定チェックポイント、ディスク staging の各キャッシュ機構の下でも、KVarN の状態契約を満たさなければならない。(SHALL) これらの機構が保持・再利用するセッション状態の互換同一性キーは、KV 形式（プリセットとテール長）、state abi、チェックポイント境界の版（`checkpoint_frontier`）をすべて含まなければならない。(SHALL) KV 形式の異なる状態（FP16 と KVarN、プリセット間、テール長間）を、どの機構を通しても相互に再利用してはならない。(SHALL) これらの機構による再利用または復元の後に greedy（temperature 0）で生成したトークン列は、キャッシュを使わない同一条件の実行のトークン列と一致しなければならない。(SHALL) 同一性キーが一致しないスナップショットとディスクキャッシュは、再利用せず再計算しなければならない。(SHALL)

#### Scenario: RAM キャッシュ経由の再利用でトークン列が一致する
- **WHEN** `--kv-cache kvarn-k6v5 --kv-cache-tail 2048` で、同じシステムプロンプトを共有する新しい会話を順に 3 つ以上実行し、3 つ目以降が共有プレフィックス全体を RAM キャッシュから復元する
- **THEN** 各応答の greedy トークン列は、キャッシュを使わない同一条件の実行と一致し、起動ログの KV 形式は `kvarn-k6v5` のままである

#### Scenario: 実行中プレフィックスの共有でトークン列が一致する
- **WHEN** `kvarn-k6v5` テール長 2048 で、同じプロンプトの要求と、同じシステムプロンプトを持つ別々の要求をそれぞれ 2 つ以上同時に送り、後続の要求が先行要求の実行中プレフィックスを共有する
- **THEN** 各応答の greedy トークン列は、キャッシュを使わない同一条件の実行と一致する

#### Scenario: KV 形式が異なるキャッシュを再利用しない
- **WHEN** `kvarn-k6v5` テール長 2048 で作成した状態を、`--kv-cache` 未指定（`fp16`）、`--kv-cache kvarn-k4v4 --kv-cache-tail 512`、`--kv-cache kvarn-k6v5`（テール長未指定）のいずれかの条件で読み込もうとする
- **THEN** いずれの条件でも状態は再利用されず、生成されたトークン列はその条件のコールド実行と一致する

#### Scenario: 同一性キーの項目が異なるビルドのキャッシュは再利用されない
- **WHEN** 同一性キーの項目が異なるビルド（`checkpoint_frontier` を含まないビルドなど）で作成した FP16 と `kvarn-k6v5` テール長 2048 の `.kvc` ディスクキャッシュを、同じ KV 形式を指定して読み込む
- **THEN** 鍵の不一致によりディスクキャッシュから再利用されず、要求は再計算で完了し、greedy トークン列は同一条件のコールド実行と一致する

#### Scenario: 履歴の編集をまたいでも一致する
- **WHEN** `kvarn-k6v5` テール長 2048 で会話を進め、直近のメッセージの編集、または以前のユーザーメッセージの編集と以降のターンの削除（学習した境界の更新）を行った後に要求を評価する
- **THEN** 応答の greedy トークン列は、キャッシュを使わない同一条件の実行と一致する

#### Scenario: ディスク staging と再起動を経由した復元で一致する
- **WHEN** `kvarn-k4v4` テール長 512 で、ディスク staging の容量を 1 GiB に制限して成長する会話のチェックポイントをディスクへ書き出し、ディスクキャッシュからサーバを再起動した後に途中の分岐を復元する
- **THEN** 復元した分岐の応答の greedy トークン列は、キャッシュを使わない同一条件の実行と一致する

#### Scenario: 封印境界をまたぐ長い履歴で一致する
- **WHEN** `--context 32768` で 16K トークンを超える履歴を、`kvarn-k4v4` テール長 512 と `kvarn-k6v5` テール長 2048 のそれぞれでキャッシュから再開し、書き換えた応答から分岐する
- **THEN** 各応答の greedy トークン列は、キャッシュを使わない同一条件の実行と一致する

## MODIFIED Requirements

### Requirement: セッション状態の整合

システムは、rollback とキャンセルをテール内の行を切り詰めるだけで完結させ、封印済みタイルを変更してはならない。(SHALL) rollback またはキャンセルの後に再計算されるクエリは、位置で決まるビューにより、中断しなかった同一セッションと同じ領域から読まなければならない。(SHALL) 継続とフォークはセッション間の独立性を保たなければならない。(SHALL) KVarN のコンパクトスナップショットは新しい版を用い、KVarN 種別、K/V ビット幅、テール長、sink・本体・テールの行数、スケール数値型を記録しなければならない。(SHALL) FP16 のスナップショットは同じコミットの upstream のビルドと同じ版とバイト列で書き出し、既存版（v1/v2）の読み込み互換を維持しなければならない。(SHALL) KVarN のプレフィックス再利用とディスクキャッシュの同一性キーには KV 形式（プリセットとテール長）を含め、プリセットまたはテール長の異なる状態を再利用してはならない。(SHALL) FP16 の同一性キーは、同じコミットの upstream のビルドが生成する同一性キーとバイト一致しなければならない。(SHALL) 復元後の全 logits は、中断しなかった同一セッションの logits とビット一致しなければならない。(SHALL) KVarN のスナップショットのバイト数は、タイル数・sink 行数・テール行数から design で定義したサイズ式で計算した値と一致しなければならない。(SHALL) 画像トークンと M-RoPE 位置を含む文脈にも同じ封印規則とビュー規則を適用しなければならない。(SHALL)

#### Scenario: キャンセルが封印をまたいでも一致する
- **WHEN** 検証窓内に位置 e_t + L + 1 を含む投機検証の直後にキャンセルし、スナップショットを保存・復元して生成を続ける
- **THEN** 封印済みタイルは変化せず、復元後の全 logits は中断しなかった同一セッションの logits とビット一致する

#### Scenario: スナップショットの保存・復元で logits が一致する
- **WHEN** KVarN セッションを保存して復元し、同じ入力を続けて評価する
- **THEN** 全 logits が中断しなかった同一セッションの logits とビット一致し、旧版スナップショットは読み込め、破損データと、KV 形式またはテール長の異なるキャッシュは拒否される

#### Scenario: FP16 の既存ディスクキャッシュが再利用される
- **WHEN** `--kv-cache` を指定せずに、FP16 の互換同一性キーとディスクキャッシュの再利用可能性を検証する
- **THEN** 同一性キーを生成する式と行の並びが同じコミットの upstream のビルドと同一であることがコード上で確認され、既存の FP16 テストが退行なく通ることで、同一性キーが一致する `.kvc` ディスクキャッシュの再利用が担保される

#### Scenario: 継続フォークが独立する
- **WHEN** 32K トークンの文脈から 2 つのブランチへ継続フォークする
- **THEN** 各ブランチの封印済みタイルとテールは他方の更新の影響を受けない

#### Scenario: 画像を含む文脈で封印が働く
- **WHEN** 画像トークンを含み M-RoPE 位置を使う文脈で、封印境界をまたいで生成する
- **THEN** 封印とビューは絶対位置の規則どおりに適用され、スナップショット復元後の logits はビット一致する
