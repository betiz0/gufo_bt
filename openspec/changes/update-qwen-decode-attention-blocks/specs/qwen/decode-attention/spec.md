# Spec Delta

## Purpose

Qwen3.8 27B の decode と検証の注意を、KV ヘッドごとにクエリヘッドを WMMA の M 次元へまとめて計算する構造に組み替え、ヘッドごとに重複している縮約とオンライン softmax の再スケールをなくす。行の独立性とビット一致を保ったまま、DFlash2 の検証コストを下げる。

## ADDED Requirements

### Requirement: 数値一致と基点の定義

この仕様で「ビット一致」は出力バイト列の完全一致を意味し、「宣言限界内で一致」は、テストのソースに定数として宣言し、根拠とともに `docs/models/qwen3.8-27b/QUALITY.md` に記録した絶対誤差または相対誤差の上限以内に収まることを意味しなければならない。(SHALL) 宣言限界は、変更を通すために緩めてはならない。(SHALL) この仕様で「基点」は、変更 `update-qwen-decode-attention-blocks` の候補が `kvarn-kv-cache-quantization` 上で分岐したリビジョンを意味し、「基点のカーネル」と「基点のビルド」はそのリビジョンのカーネルとビルドを意味しなければならない。(SHALL) `main` と `upstream/main` は KVarN を含まないため、この仕様の比較の対照にしてはならない。(SHALL)

#### Scenario: 宣言限界が記録されている
- **WHEN** この変更で追加または変更した、「宣言限界内で一致」を判定する各テストを確認する
- **THEN** テストのソースに上限値の定数があり、同じ値と根拠が `docs/models/qwen3.8-27b/QUALITY.md` に記録されている

#### Scenario: 基点が記録されている
- **WHEN** この変更のゲートの成果物を確認する
- **THEN** 基点のリビジョンのハッシュが記録され、比較の対照はすべて基点のカーネルまたは基点のビルドである

### Requirement: KV ヘッドごとのブロック

FP16 KV で系列長 128 以上の decode と検証の注意（split-K の作業領域が与えられる経路）は、1 ブロックが 1 つの（KV ヘッド, 行, パーティション）を受け持たなければならない。(SHALL) ブロックは、その KV ヘッドを共有する 6 個のクエリヘッドを WMMA の M 次元に並べなければならない。(SHALL) その KV ヘッドの K と V のタイルは、グローバルメモリから 1 ブロックにつき 1 回だけ共有メモリに読み込み、6 個のクエリヘッドで共有しなければならない。(SHALL) 各クエリヘッドの softmax と値の蓄積は、他のクエリヘッドの値に依存してはならない。(SHALL)

#### Scenario: 6 ヘッドが 1 回のタイル読み込みを共有する
- **WHEN** 系列長 128 以上で 1 行の decode を実行するカーネルのコードを確認する
- **THEN** K・V の各タイルをグローバルメモリから共有メモリへ読み込む処理は 1 ブロックにつき 1 回だけ実行され、6 個のクエリヘッドのスコアと値の積和はその共有メモリから WMMA で計算され、各クエリヘッドの出力は単独のクエリヘッドとして計算した FP64 参照と宣言限界内で一致する

### Requirement: パーティションの不変条件

各行のパーティションは、その行の系列長 n だけから決めなければならない。(SHALL) パーティション数は 32 以下でなければならない。(SHALL) 各パーティションの境界は 128 の倍数の位置でなければならず、最後のパーティションの終端だけが n であってよい。(SHALL) 0 から n − 1 までの各位置は、ちょうど 1 つのパーティションに属さなければならない。(SHALL) 部分注意の統合は R によらず同じ算術で行い、キーを持たないパーティションを結果に寄与させてはならない。(SHALL) 同じ起動で処理する行のパーティションが互いに異なっても、各行の出力はその行を単独で計算した出力とビット一致しなければならない。(SHALL)

#### Scenario: 境界がタイル境界に整列する
- **WHEN** 系列長 128、129、4096、4097、131064、131072、262143、262144 で 1 行の decode を実行し、各パーティションの範囲を記録する
- **THEN** 各系列長でパーティション数は 32 以下であり、各パーティションの境界は 128 の倍数（最後の終端は n）で、0 から n − 1 までの各位置はちょうど 1 つのパーティションに属する

#### Scenario: キーを持たないパーティションが結果に寄与しない
- **WHEN** 選んだ分割の方式がキーを持たないパーティションを生じる系列長（方式 B なら 128、129、4095）で decode を実行する
- **THEN** 出力はすべて有限であり、FP64 参照と宣言限界内で一致する

#### Scenario: パーティションの違う行を同じ起動で処理する
- **WHEN** 系列長 4096 の行と 4097 の行を同じ検証起動で処理する
- **THEN** 各行の出力は、その行を単独で計算した出力とビット一致する

### Requirement: 行の独立性

各行の結果は、同じ起動の他の行の値と行数 R に依存してはならない。(SHALL) 検証行の logits は、同じ位置のスカラー decode の logits とビット一致しなければならない。(SHALL) head_dim 方向の分担、タイルの分割、WMMA の累算順序、縮約の木は R によらず同じでなければならない。(SHALL) WMMA の外で行うスカラーの積和（オンライン softmax の再スケール、部分注意の統合、タイルごとの後処理）は、明示的な `fmaf` で固定しなければならない。(SHALL)

#### Scenario: 行数によらずビット一致する
- **WHEN** R ∈ {1, 2, 3, 8} で、開始位置を `kv_storage_ops_test` の集合と 4093・4095・4096・4097・131064 として検証の注意を実行する
- **THEN** 各行の注意出力は、同じ行を R=1 で計算した注意出力とビット一致する

#### Scenario: 検証行がスカラー decode と一致する
- **WHEN** ドラフト幅 2〜8 の検証行を因果 decode で計算する
- **THEN** 各行の logits は同じ位置のスカラー decode の logits とビット一致する

### Requirement: 精度の非劣化

注意出力は、FP64 の参照に対する最大絶対誤差と RMS 誤差が、同じ入力に対する基点のカーネルの値以下でなければならない。(SHALL) 比較は R=1 で、系列長 128、129、4096、4097、32768、131072 のそれぞれについて、`tests/models/qwen/hip/attention/long_context_ops_test.cpp` と同じ生成式の入力（以下、飽和しない入力）と、P と Q の残差が f16 の非正規化数の範囲に入る小さな値を含む入力の両方で行わなければならない。(SHALL) 採否は FP64 との誤差で決めなければならない。(SHALL) Q と P を f16 の上位と残差に分けない版は、単体ベンチで速度の参考として測るだけにし、本番のコードに含めてはならない。(SHALL)

#### Scenario: FP64 参照に対して基点以下である
- **WHEN** 飽和しない入力と、f16 の非正規化数の範囲に入る小さな値を含む入力で、系列長 128、129、4096、4097、32768、131072 の R=1 の decode を基点のカーネルと新しいカーネルで実行し、それぞれの FP64 参照との最大絶対誤差と RMS 誤差を測る
- **THEN** 各系列長・各入力で、新しいカーネルの両方の誤差が基点のカーネルの値以下であり、長文脈の既存テストの 5e-4 の許容誤差が緩められていない

### Requirement: 変更しない経路

系列長 128 未満のオンライン経路、HIP グラフの経路、FP32 参照 KV の経路は変更してはならない。(SHALL) MTP の予測器自身の注意は FP32 参照 KV の経路に入るため、その経路の算術を変更してはならない。(SHALL) FP32 参照 KV の経路と、KVarN の読み出しが使う分割と統合の算術は、変更してはならない。(SHALL) これらの経路の出力は、同じ入力に対して基点のビルドとビット一致しなければならない。(SHALL)

#### Scenario: 短い文脈では既存の経路が使われる
- **WHEN** 系列長 127 の decode を、同じダンプのソースを基点と候補のソースツリーでそれぞれビルドして実行する
- **THEN** 系列長 128 未満のオンライン経路が使われ、両者の出力ファイルはバイト一致する

#### Scenario: グラフ捕捉と MTP の注意が影響を受けない
- **WHEN** HIP グラフ経路で decode を捕捉し、MTP の予測器と同じ引数（FP32 と FP16 の両平面）で注意を基点と候補のビルドで実行する
- **THEN** グラフの拒否理由は増えず、FP32 参照 KV の経路が選ばれ、その出力は基点のビルドとバイト一致する

#### Scenario: KVarN の読み出しは変わらない
- **WHEN** FP16 の注意を置き換えたビルドで、CPU の参照エンコーダで封印した固定の入力の KVarN の decode と検証行の読み出しを、基点と候補のビルドで実行する
- **THEN** 両者の出力はバイト一致し、KVarN の互換同一性は基点と同じである

### Requirement: FP16 の互換同一性の更新

FP16 の decode と検証行の注意を置き換えたビルドは、`qwen/kv-cache-quantization` の「セッション状態の整合」に従い、FP16 の互換同一性に decode と検証行の注意の算術を表す項目を加えなければならない。(SHALL) この項目は、FP32 と KVarN の互換同一性に加えてはならない。(SHALL)

#### Scenario: 基点の FP16 キャッシュが再利用されない
- **WHEN** 基点のビルドで `--cache-disk` を指定して作った FP16 の `.kvc` ディスクキャッシュを、FP16 の注意を置き換えたビルドで同じディレクトリと同じ構成を指定して読み込み、同じ要求を送る
- **THEN** 互換同一性の不一致によりディスクキャッシュは再利用されず、要求は再計算で完了し、greedy トークン列はキャッシュを使わない同一条件の実行と一致する

#### Scenario: FP32 と KVarN の互換同一性は変わらない
- **WHEN** FP16 の注意を置き換えたビルドで、FP32 と KVarN の各プリセットの互換同一性を基点のビルドと比べる
- **THEN** バイト列は一致する

### Requirement: 旧カーネルの削除

各段階を採用した場合、その段階で置き換えた旧カーネルを削除しなければならない。(SHALL) Phase 1 では FP16 の split-K の部分注意カーネルを削除しなければならない。(SHALL) 切り替えのオプションと環境変数を残してはならない。(SHALL)

#### Scenario: 採用後に選択経路が 1 つだけになる
- **WHEN** Phase 1 を採用したビルドで decode の注意の起動経路と `--help` を確認する
- **THEN** 系列長 128 以上の FP16 の decode と検証の注意カーネルの選択肢は 1 つで、切り替えのオプションと環境変数は存在しない

### Requirement: 単体ベンチのゲート（FP16）

変更 `update-qwen-decode-attention-blocks` の Phase 0 の FP16 のゲート（G0F）は、次をすべて要求しなければならない。(SHALL) 精度の非劣化。R ∈ {1, 2, 3, 8} と `行の独立性` の開始位置での行の独立性。R=1・深度 128K の resident の 1 層分の時間が 0.72 ms 以下であること。R=8 の cold の時間が深度 32K と 128K で基点のカーネルの 0.5 倍以下であること。R=1 の cold の時間が深度 32K と 128K で基点のカーネルの 1.03 倍以下であること。resident の時間は、1 層分の KV が SoC のキャッシュに収まる文脈（2304〜9216 トークン）を掃引し、（クエリヘッド, キー）あたりの単位コストを最小二乗で当てはめて深度 128K に換算した値としなければならない。(SHALL) これらの閾値と評価点は測定の前に固定した値であり、結果を見て変更してはならない。(SHALL)

#### Scenario: G0F の結果が記録される
- **WHEN** G0F を単体ベンチで判定する
- **THEN** 各項目の測定値、対照、閾値、達成・未達、VGPR 数と占有が成果物に記録され、判定に使わない記録として深度 128・512・4096 の R=1 の cold の時間が併記される

### Requirement: 本番のゲート（FP16 の品質）

変更 `update-qwen-decode-attention-blocks` の FP16 の経路の本番化（G1F）は、Qwen3.8 27B の Q8_0 の重みで、`tools/qwen27b/check.py` の `kernels`・`model`・`multi-session`・`serving` の各スイートに通ることを要求しなければならない。(SHALL) あわせて、`tests/functional/` の `long-context` と `cache` のスイートに、AR と DFlash2 の各モードで通ることを要求しなければならない。(SHALL)

#### Scenario: FP16 の品質の判定が記録される
- **WHEN** FP16 の経路の品質を Q8_0 の重みで判定する
- **THEN** 各スイートの合否とスキップの一覧が、モデルの SHA-256 と基点のリビジョンとともに記録され、すべて合格している

### Requirement: 本番のゲート（FP16 の速度）

G1F は、Qwen3.8 27B の Q8_0 の重みで次をすべて要求しなければならない。(SHALL) C1 の AR の tg と pp に、`docs/models/qwen3.8-27b/BENCHMARKS.md` の単一利用者の全深度で基点との有意な退行が無いこと。C8 の AR と DFlash2（利用者あたり文脈 4096）に基点との有意な退行が無いこと。C1 の DFlash2 の tg が深度 32K・64K・128K で基点より有意に改善すること。有意な差は `測定方法` の定義に従わなければならない。(SHALL) DFlash2 の判定は、文脈コスト表を新しいカーネルで測り直したビルドで行わなければならない。(SHALL)

#### Scenario: FP16 の速度の判定が記録される
- **WHEN** FP16 の経路の速度を判定する
- **THEN** C1 の AR・DFlash2 の tg と pp、C8 の AR と DFlash2 の基点との比較が、リクエスト・フェーズごとの時間差、モデルの SHA-256、基点のリビジョン、測定条件とともに記録され、有意な差の判定が 5% と 3 ms の両方で行われている

### Requirement: 測定方法

変更 `update-qwen-decode-attention-blocks` の Phase 0 の測定は、基点のカーネルを逐語コピーした対照と比べ、cold と resident の両方を測り、5 回以上の中央値を取らなければならない。(SHALL) FP64 の参照と、飽和しない入力を用いなければならない。(SHALL) 本番の測定は `docs/models/qwen3.8-27b/BENCHMARKS.md` と同じ方法で、同じ測定系列の基点のビルドと交互に行い、リクエスト・フェーズごとに比べ、リクエスト間で平均してはならない。(SHALL) 本番の有意な差は、リクエスト・フェーズごとの時間の差が 5% と 3 ms の両方を超える場合としなければならない。(SHALL) GPU を使う測定は、他の GPU ジョブや、もう一方のモデル（Qwen3.8 Flash-Next）の測定と時間を重ねてはならない。(SHALL)

#### Scenario: Phase 0 の再現手順が記録されている
- **WHEN** Phase 0 の測定の成果物を確認する
- **THEN** 基点のリビジョン、対照のカーネル、cold と resident の別、resident の掃引範囲、繰り返し数、入力、FP64 参照の条件が、そのまま実行できる形で記録され、再実行で精度の値は同一になり、時間は 5 回以上の中央値として記録される

### Requirement: DFlash2 制御器の文脈コストの再測定

27B のカーネルを採用するビルドでは、DFlash2 制御器の文脈コストの実測表を新しいカーネルで測り直した値にしなければならない。(SHALL) 測り直しは既存の表と同じ方法（cold の KV、16 フル注意層、2K から 32K への追加コストを約 100 ms の浅いサイクルに対する相対値で表す。`docs/models/qwen3.8-27b/artifacts/q4-dflash2-c1-focused.json` の `controller_cost_calibration`）で行わなければならない。(SHALL) 採用しなかった場合は表を変更せず、理由を記録しなければならない。(SHALL)

#### Scenario: 採用するビルドの表が更新される
- **WHEN** 新しいカーネルを含むビルドで、2K から 32K への追加コストを、アンカーと 1〜7 個の提案の各行数で既存の表と同じ方法で実測する
- **THEN** 制御器の表が新しい測定値で更新され、測定条件とともに記録され、本番の DFlash2 の判定はこの表を含むビルドで行われる

### Requirement: 結果の記録と未達時の扱い

採用の可否とゲートの測定値を、`docs/models/qwen3.8-27b/` の `BENCHMARKS.md`、`EXPERIMENTS.md`、`QUALITY.md` に記録しなければならない。(SHALL) KVarN の FP16 比（G1R の測り直し）は、`docs/models/qwen3.8-27b/README.md` と `docs/CLI.md` にも記録しなければならない。(SHALL) FP16 の互換同一性の更新と、基点より前のビルドと upstream のビルドで作った FP16 のディスクキャッシュが再利用されず再計算になることは、`docs/models/qwen3.8-27b/README.md` と `docs/CLI.md` に記録しなければならない。(SHALL) ゲートに届かなかった場合は、その時点で作業を止め、測定値・原因の分析・考えられる選択肢を利用者に返さなければならない。(SHALL) 利用者の判断なしに、基準の変更、予定外の最適化の継続、変更の中止を行ってはならない。(SHALL)

#### Scenario: 記録が残る
- **WHEN** この変更を完了する
- **THEN** 採用の可否、ゲートの測定値、不採用の場合はその理由が上記の文書に記録され、未達で止めた場合は利用者への報告が残っている
