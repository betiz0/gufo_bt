# Design

## Context

現行の KV 経路（すべて読み取り確認済み）:

- ストレージ選択は `QwenExecutionPolicy::kv_cache_storage`（`src/models/qwen/hip/execution_policy.hpp`）の `QwenKvCacheStorage{kFp32,kFp16}` のみ。production の値は `inference_backend.cpp:889` の `QwenExecutionPolicy::Production()` にハードコードされ、`--kv-cache` に相当する実行時スイッチは存在しない（`src/` に KV dtype を選ぶ環境変数はない）。`Fingerprint()` は `UsesFp16AttentionKv()` をビット 8 に置く。
- KV 領域は層 × KV ヘッドごとに絶対位置 `[max_context][num_kv_heads × head_dim]` の連続平面（`GetAttentionKvPlaneElements()`）。確保は `arena.cpp` の `d_attention_kv_f16`（`total_kv * 2 byte * 2`）。
- 注意カーネルは `(float* k_cache, float* v_cache, void* k_cache_f16, void* v_cache_f16)` の 4 平面を引数に取る（`ops/attention.hpp`）。decode は `attention_decode.hip` のスカラー版・split-K 版（`kSplitKDecodeAttentionMaxSplits{32}`、最小文脈 128）、グラフ版は `attention_decode_graph.hip`、検証行は `LaunchCausalDecodeAttention`、prefill は `attention_tile.hip` / `attention_wmma.hip` / `attention_batched.hip`。tile は永続 FP16 平面へ、WMMA は一時 FP16 ワークスペース（ヘッドを有界なグループ単位で再利用）へパックする。
- GEMM 経路 `LaunchBatchedAttentionGemm` は FP32 head-major 平面だけを読み、呼び出し元は `tests/models/qwen/hip/attention/backend_ops_test.cpp` のみ（production 経路ではない）。
- split-K decode は HIP グラフ捕捉の対象外（`QwenGraphRejection::kSplitKAttentionRequired`）。
- 形状: tile 経路の定数は Q 24 ヘッド・KV 4 ヘッド・head_dim 256（`detail/attention_policy.hpp`）。27B のフル注意層は 16（`block_count = 65` − MTP 1 層 = 64 層、`full_attention_interval = 4`、`tests/core/gguf_reader_test.cpp:267-320`）。FP16 KV は 1 トークンあたり 16 × 4 × 256 × 2 × 2 = 64 KiB、262,144 トークンで 16 GiB。
- prefill のチャンクは最大 `kMaxPromptBatch = 4096` 行（`arena.cpp:20`）。DFlash の検証は 1 セッションあたり最大 8 行（`inference_backend.cpp:1480`）。
- 巻き戻し: 投機検証後のキャンセル（`PrepareCancellation`、`inference_backend.cpp:667-690`）は、その検証ステップで受理した最大 `kQwenMaxResumeTokens = 9` トークンを巻き戻す。`SaveState`/`RestoreState` は再帰状態だけを保存し、KV は「append-only で、各注意は明示位置で上限が決まる」ことを前提に保存しない（`ssm_replay.cpp:50-51`）。
- スナップショット: コンパクト版は magic + `kCompactSnapshotVersion{1}`（v2 も受理）+ 80 バイトヘッダで、`kv_storage` を値域チェックし、`live_kv_elements_per_plane` と payload 長の整合を検証する。永続版（`kQwenPersistentPayloadVersion = 3`）はこの payload を内包する。プレフィックス再利用の同一性キーは `QwenCompatibilityIdentity` の `kv_storage=fp16|fp32` と `state_abi=`。
- 他モデルの KV 形式: Flash-Next は F16、DeepSeek V4 Flash は FP8。
- 既存の量子化資産: `src/core/quant/ggml_dequant.{hpp,cpp}` に GGML ブロックの CPU オラクル。非対称 RTN の量子化器は存在しない。Hadamard の前例は DeepSeek V4 Flash の indexer FP4 経路のみで、Qwen には存在しない。

制約: production は gfx1151 + HIP のみ（Triton/AOTriton/CK/MIOpen を依存にしない）。1 挙動 = 1 正規ロングオプション（エイリアス禁止）。production に環境変数スイッチや試験用経路を残さず、不採用経路は削除する。KVarN の実装・CPU オラクル・テスト・ツールは Qwen のモデルツリーに置き、他モデルとカーネルを共有しない。実効 bpv はメタデータ込みで報告し、decode・検証では逆量子化値をグローバルメモリに実体化しない。

## Goals / Non-Goals

**Goals:**

- フル注意層 KV を 262,144 トークン容量で、テール長の全範囲（未指定および 256〜2048）で、メモリ優先プリセット本体 4.5 bpv 以下（総量 4.6 bpv 以下）、品質優先プリセット総量 6.4 bpv 以下に収める。
- FP16 KV を教師とする一致トークン比較で、各プリセットの適合テール長で、品質優先プリセットが q8→q4 内分位置 p ≤ 0.15（q8_0 に近い）、メモリ優先プリセットが p ≤ 1（q4_0 相当以上）を満たす（D17）。
- テール長をユーザーが `--kv-cache-tail` で選び、品質とメモリのトレードオフを調整できるようにする。
- decode・検証・prefill・巻き戻し後の再計算で同一の「位置で決まるビュー」と 3 領域オンライン softmax を使い、AR と DFlash2 の greedy 一致とスナップショット復元のビット一致を KVarN 下でも保つ。
- 既定 `fp16` と既存バイト列・FP16 の互換同一性キー・旧スナップショット版・既存 `.kvc`・既存 CLI 挙動を維持する。

**Non-Goals:**

- DFlash2 ドラフト・MTP 層の KV、Qwen3.8 Flash-Next、DeepSeek V4 Flash、音声・画像・動画モデルの KV 量子化。
- Gated DeltaNet の再帰状態（`QwenRecurrentStateStorage` は不変）。
- FP16 経路の数値変更（回転は KVarN 選択時のみ適用し、既存 golden のビット一致を保つ）。
- 既定値の `fp16` からの昇格、CPU 参照実装の production 化。
- FP16 スナップショットから KVarN への変換復元（旧 D-06）。形式の異なる状態は同一性キーで分離され、再利用されないため、変換がなくても誤った状態は読まれない。
- 層別ビット割当。
- スケール類の FP32 化（本体 4.875 bpv となり、メモリ優先プリセットの 4.5 bpv 基準を満たせないため）。

## Decisions

### D1. KV を 3 領域に分離し、F16 行を sink + マージン付きテールリングに縮める

KVarN 選択時は次の 3 領域を確保する（層 × KV ヘッド単位）。

| 領域 | 内容 | サイズ |
|---|---|---|
| sink | 絶対位置 0〜127 の F16 行（回転済み） | 128 行/ヘッド |
| 本体 | 封印済みタイル（128 トークン × 256 チャネルの量子化コード + スケール・ゼロ点 + 正規化スケール） | `ceil((max_context-128)/128)` タイル/ヘッド |
| テール | 絶対位置ベースのリング、容量 C = L+128+W 行の F16（回転済み） | C 行/ヘッド |

テール長 L は `--kv-cache-tail` で指定する（D10）。未指定のときはテールトークンを追加せず、L は構造上の最小値 W とする。指定時は 256 以上 2048 以下の整数とする。W は最大検証行数と最大巻き戻しトークン数の大きい方で、現行値では `kQwenMaxResumeTokens = 9`。リング位置は `(pos - 128) mod C`。L は実行時の値になるため、`static_assert` では指定可能な下限 256 ≥ W を検査し、L の範囲と C = L+128+W はポリシー構築時に検査して、テールはセッション生成時に C 行で確保する。L = W でも、128 行が揃っていないタイルの行と、ビュー規則がまだ F16 で読む行（最初の封印以後、クエリから見て W+1 行以上 W+128 行以下）は F16 で保持する。封印は 128 行が揃い、かつビュー規則で量子化読み出しに入ったタイルに対してだけ行う。

必要容量の根拠: 直前の確定位置を p とすると、次のステップ（または巻き戻し後の再実行）で計算されるクエリは p+1〜p+W。これらのクエリが F16 で読む最古の行は、ビュー規則（D2）により p−L−126 以降であり、書き込まれる最新行は p+W。よって F16 で同時に必要な行数は L+W+127 ≤ C で、新しい行の書き込みがまだ必要な F16 行を上書きすることはない。キャンセルが巻き戻すのは直前の検証ステップだけなので、巻き戻し後に再計算されるクエリも同じ範囲に収まる。

F16 行は sink もテールも回転済みの値を格納する（注意スコアは回転空間で計算するため、非量子化行だけ無回転にすると整合しない）。

テール長と総量 bpv（262,144 トークン容量、FP16 スケール、D5 のサイズ式）。この容量ではセッションあたり KV 容量（GiB）が総量 bpv と同じ数値になる。

| プリセット | 本体 bpv | 未指定（L = W） | L = 256 | L = 1024 | L = 2048 |
|---|---|---|---|---|---|
| `kvarn-k4v4` | 4.4375 | 4.45 | 4.47 | 4.51 | 4.58 |
| `kvarn-k5v4` | 4.9375 | 4.95 | 4.97 | 5.01 | 5.08 |
| `kvarn-k5v5` | 5.4375 | 5.45 | 5.47 | 5.51 | 5.58 |
| `kvarn-k6v5` | 5.9375 | 5.95 | 5.97 | 6.01 | 6.08 |

上限 2048 は、`kvarn-k4v4` の総量 4.6 bpv 基準を満たす L の上限 2432 から決めた。この上限により、メモリ優先・品質優先の bpv 基準はテール長の全範囲で成り立つ。

代替案:
- テール長を定数にする方式（旧 D-03）は、品質とメモリのトレードオフを利用者が選べない。G0（L = 128）では品質優先の基準に届かず、テールの長さで品質を補う余地を残せない。
- 上限を 4096 にする方式は、`kvarn-k4v4` の総量が 4.70 bpv となり、4.6 bpv 基準を満たせない。
- 既存の絶対位置 F16 平面を残して封印分だけ別領域に置く方式は、F16 行を max_context 分確保し続けるため、メモリ優先プリセットの bpv 基準を満たせない。
- 容量 L+128 のリング（マージンなし）は、確定済みテールが L+127 行のときに 2 行目の検証行が未封印の最古行を上書きし、封印をまたぐキャンセル後に F16 ビューを復元できない。
- 領域タグ付き可変長にする方式は、split-K と prefill のタイル反復に分岐を持ち込み、経路間の不整合の原因になる。

### D2. ビューとタイル番号を絶対位置だけから導出する

タイル t は絶対位置 `[128 + 128t, 128 + 128t + 127]` を担当し、`t = (pos - 128) / 128` で一意に決まる。最終位置を e_t = 128 + 128t + 127 とする。クエリ位置 q は、e_t ≤ q − L − 1 のタイルを量子化値で読み、それ以外の行（sink、未封印・F16 保持中の行）を F16 で読む。

この規則はクエリ位置だけで決まるため、AR decode、検証行、prefill の各行、巻き戻し後の再計算が同じビューを使う。これにより AR と DFlash2 の greedy 一致、チャンク不変性、キャンセル後のビット一致が同時に成り立つ。最初の封印以後、クエリから見たテールは L+1 以上 L+128 以下の行になる。

代替案:
- 封印カウンタでビューを決める方式は、チャンク境界や検証幅、巻き戻しの有無でカウンタ進行がずれ、同じ位置のクエリが異なる領域を読む。
- 封印を commit 直後に行い、その時点の封印状態でビューを決める方式は、検証窓の中で AR と異なるビューになる。

### D3. 回転は書き込み融合カーネルで行い、逆回転は 1 箇所だけ

- K/Q/V の head 単位チャネル方向正規化 Hadamard（head_dim 256、8 段の LDS butterfly、対称行列なので逆変換も同じ演算、スケール 1/√256）を、既存の QK RMSNorm + RoPE + KV 書き込み融合カーネル（`kernels/fused.hip`、`kernels/prefill_rope.hip`）のレジスタ値に対して適用する。これにより GGUF 重みは変更しない。
- 注意出力側では、softmax 加重和の直後に 1 回だけ逆回転してから SiLU ゲートへ渡す。LSE で部分注意をマージする経路ではマージ後に 1 回だけ適用する。逆回転は線形なので、sink・本体・テールの統合結果に対して 1 回で足りる。
- 代替案: K のみ回転する方式は、V の外れ値チャネルが分散されないため、V の量子化誤差が大きくなる。重み側を事前回転する方式は GGUF を変更するため不可。

### D4. 封印は位置で決まる述語つきの無条件カーネルで、注意の前に行う

- decode と検証のステップでは、先頭で封印カーネルを無条件に 1 回起動する。カーネルはデバイス上のステップ最大クエリ位置 q_max と封印済みタイル数を読み、e_t ≤ q_max − L − 1 かつ未封印のタイルだけを封印して、それ以外は即座に return する。対象タイルの行は位置 e_t ≤ q_max − L − 1 ≤ p − 1（L ≥ W）なので、すべて確定済みである。
- 分岐はホストではなくカーネル内に置くため、HIP グラフの捕捉構造がトークン数に依存せず、ホスト同期も追加されない。
- 封印済みタイルは巻き戻しでも変更しない。巻き戻し後に再計算されるクエリは、D2 の規則によりまだそのタイルを F16 で読むため、F16 行が D1 のリングに残っていれば結果は一致する。
- prefill チャンクは、層ごとに「チャンクの KV 書き込み → そのチャンクの q_max で封印対象となるタイルの封印 → クエリごとのビューで注意」の順に処理する。チャンク内の行は有界なチャンク用ワークスペース（最大 `max_batch` 行）に F16 で保持し、リングにはチャンク末尾の C 行を残す。
- 代替案: ホスト側で `valid_context` を見てカーネルを追加投入する方式は、グラフ捕捉時に到達不能な分岐となり捕捉を拒否させる。commit 直後に封印する方式は、D2 の代替案で述べたとおり検証窓内でビューがずれる。

### D5. タイルのパラメータ配置は K をチャネル単位、V をトークン × グループ単位にする

- タイル内で二軸分散正規化（チャネル方向とトークン方向の標準偏差を対数領域で交互に 16 回、縮約順序は固定）を行い、チャネル正規化スケール 256 本とトークン正規化スケール 128 本を得る。
- K は非対称 RTN をチャネル単位（トークン方向 128 要素でパラメータ共有）、V はトークン単位（チャネル方向のグループ 128）で量子化する。
- 読み出し時: K はチャネルスケールとゼロ点をクエリ側へ折り込み、トークンスケールをスコアに乗じる。V は正規化空間のまま蓄積し、トークン単位のスケール・ゼロ点を確率重みに、チャネルスケールをタイル単位で適用する。
- スケール型は FP16 とする（D-04: G0 の観測で FP16 オーバーフローは 0 件、アンダーフローは ε 下限とゼロ点に限られ実データのダイナミックレンジ不足がないため BF16 へは変更しない）。FP32 は選択肢から外す（本体 4.875 bpv となり 4.5 bpv 基準を満たせない）。
- サイズ式（FP16/BF16 スケール時、1 タイル・1 KV ヘッド・K または V あたり）: コード `128 × 256 × b` bit + スケール・ゼロ点 8,192 bit + 正規化スケール 6,144 bit。4 bit で 4.4375 bpv。総量 bpv は（タイル数 × タイル bit + (128 + C) × 16 × 256 bit）を容量 × 256 で割った値。C = L+128+W なので、総量 bpv はテール長とともに増える（D1 の表）。スナップショットのサイズも、使用中のタイル数・sink 行数・テール行数からこの式で計算する。
- 代替案: 対称 RTN はゼロ点を持たず、非対称な分布の K でレンジを無駄にする（品質差はフェーズ 0 で確認する）。K もトークン単位にすると 128 倍のパラメータになり、メタデータの bpv が基準を割る。
- 5 bit・6 bit は 4 bit の下位ビット面 + 追加の上位ビット面として格納し、4 bit 経路のロード幅と整列を維持する。代替案: 3 バイト詰めのインターリーブはベクタロードを崩す。

### D6. 二軸正規化の反復回数・縮約順序はコンパイル時定数として固定し、オラクル比較は 2 段で行う

- 反復 16 回、ε 下限、クランプ、非有限値検出を定数として定義し、チャネル方向・トークン方向の縮約は固定順（チャネル昇順 → トークン昇順）で行う。これにより封印結果がハードウェアの並列度やワークグループ構成に依存せず、GPU 同士の封印はビット一致する。
- T-01 の CPU オラクル比較は 2 段で行う。(1) GPU が出力した正規化スケール・スケール・ゼロ点を CPU オラクルに入力し、量子化コードが完全一致することを確認する。(2) スケール類そのものは、CPU の倍精度計算に対する宣言限界（相対誤差）内であることを確認する。
- 代替案: 反復回数を収束判定で可変にする方式は、封印結果が入力に依存して計算時間が変わり、グラフ内の処理量も不定になる。CPU と GPU の全ビット一致を要求する方式は、CPU 側でデバイスの log・exp・sqrt と丸めを再現する必要があり、オラクルの独立性も失われる。

### D7. 読み出しは Qwen 専用の共有ヘルパに集約し、decode・検証では逆量子化を実体化しない

- `src/models/qwen/hip/kernels/kvarn_seal.hip`（封印）と `kernels/kvarn_read.hip`（タイルのコード・スケール読み出し、D2 のビュー判定、3 領域オンライン softmax 用の共通デバイス関数）を追加し、起動関数は `ops/kvarn.hpp` に置く。
- decode（スカラー / split-K / グラフ版）と検証行は共通ヘルパを通じてタイルを直接読み、逆量子化テンソルをグローバルメモリへ書かない。
- prefill の tile 経路と batched 経路は、キーブロック単位でタイルを LDS へ逆量子化して読み、永続 FP16 プレフィックスを実体化しない（現行の `SyncTiledAttentionKvPrefixKernel` が前提とする FP16 プレフィックスは KVarN では存在しないため、この同期カーネルは KVarN 経路では使わない）。WMMA 経路は既存の一時 FP16 パックワークスペース（ヘッドを有界なグループ単位で再利用）へ逆量子化してから WMMA へ渡す。永続 KV 領域へは書き戻さない。
- prefill の各クエリ行は D2 のビューに従い、同じタイルを行によって量子化値または F16 で読む。
- GEMM 経路は production の読み出し契約に含めず、KVarN 選択時は明示的なエラーとする。
- tile 経路の対応判定（`IsTiledAttentionSupported(const AttentionSupportParams&)` の FP16 平面非 null 条件）は、KVarN では封印タイル平面を指すように更新する。
- 検証行（最大 8 行）は同一タイルの逆量子化結果を LDS で共有する。
- KVarN が対応しない形状（Q 24 / KV 4 / head_dim 256 以外）はポリシー構築時に検出し、起動時エラーとする。
- decode と検証行の算術は D5 の折り込みで行う。K はタイルごとにチャネルスケール・RTN スケールをクエリ側へ、ゼロ点の寄与をタイル単位の定数項へ折り込み、要素ごとの処理をコードの展開と 1 回の積和にする。V はタイル内を正規化空間で蓄積し、トークン単位のスケール・ゼロ点を確率重みへ、チャネルスケールをタイル単位で適用する。online・split-K・検証行の 3 経路は同じ式と同じ演算順序を使い、乗算と加算の融合は明示的な `fmaf`（FP16 decode の既存の書き方）で固定して、経路間のビット一致（T-05）を保つ。
- 代替案: 経路ごとに独立実装すると出力不一致の温床になる。全経路で FP16 ワークスペースへ逆量子化すると帯域削減が失われ、長文脈の性能基準を満たせない。要素ごとに `(code × s + z) × channel_scale` を作ってから内積を取る方式（G1 の 1 回目の実装）は、要素あたりの演算が K で約 7、V で約 8 になり、長文脈で計算律速になる（D18）。ファイル全体で FP の収縮を無効化する方式（`#pragma clang fp contract(off)`）は、経路間の一致は保てるが、すべての積和を乗算と加算の 2 命令にする。複数キー（2・4・8）をまとめて縮約と再スケールを行う方式は、ブロックごとの最大値と再スケールの処理が増え、キーごと処理より遅かった（D19）。

### D8. split-K の分割境界をタイル境界に整列させる

split 境界を 128 トークン単位に丸め、各 split が整数個のタイルを担当し、末尾 split がテール行を吸収する。分割数を選ぶ方針（`SelectDecodeAttentionSplitCount`、最小文脈 128、上限 32）と `DecodeAttentionScratchElements` のレイアウトは維持し、境界だけをタイル境界へスナップする。グラフ経路は split-K を捕捉できないため、グラフ経路はオンラインカーネルで 3 領域を読み、整列の対象はスカラー / split-K / 検証行の経路とする。代替案: 均等分割のままだとタイルが 2 つの split にまたがり、部分タイルの読み出しとスケール適用が二重化する。

### D9. KVarN だけ新しいスナップショット版と同一性キーを使い、FP16 は変更しない

- KVarN のコンパクトスナップショットに版 3 を追加し、KVarN 種別、K/V ビット幅、テール長 L、W、sink・本体・テールの行数、スケール数値型、タイル数とスケール数を記録する。v3 は自前のヘッダ長・オフセットを持ち、版ごとに検証する。
- FP16・FP32 のスナップショットは変更前と同じ版（v1）とバイト列で書き出し、v1/v2 の読み込みも維持する。永続スナップショットのヘッダと版も FP16 では変更せず、KVarN のときだけ内包する v3 payload の検証に追従する。
- `QwenCompatibilityIdentity` の `kv_storage=` と `QwenStateAbi` は、FP16・FP32 では変更前と同じ文字列を出す。KVarN では `kv_storage=` にプリセット（種別 + K/V ビット + テール長 L + スケール型。テール長は未指定と指定値を区別する）を含む値を、state_abi に KVarN 用の値を出す。これにより既存の `.kvc` は再利用でき、形式の異なるキャッシュは破損ではなく明示的な不一致として拒否される。
- 代替案: v1 ヘッダを拡張すると既存リーダーが壊れる。全形式でキー書式を更新すると既存の `.kvc` がすべて無効になり、既定挙動の不変という Goal に反する。

### D10. CLI は `--kv-cache` 1 つに集約し、フェーズ 0 で先に配線する

- `--kv-cache <format>`（値: `fp16` / プリセット名、Qwen3.8 27B の既定 `fp16`）を、`serve llm` の実パーサと help 専用パーサの両方、`prompt` と `chat` が共有する `RegisterTextOptions`、`bench` の `RegisterBenchOptions` に登録する。ショート名は空（`""`）とし、エイリアスを作らない。help 専用パーサへの登録漏れは `--help` からオプションが消えるサイレント故障になるため、両方を必須とする。
- 解析後の検証で未知の値を拒否し（既存の終了コードとヘルプの流儀に合わせる）、解決済みの記述子を `InferenceBackend::load` 経由で `QwenTextRunner` に渡して `QwenExecutionPolicy` を組み立てる（`inference_backend.cpp:889` のハードコードを置き換える）。
- Qwen3.8 27B 以外のモデルで `--kv-cache` が明示指定された場合は、値にかかわらず起動時エラーとする。これらのモデルは起動ログにモデル固有の KV 形式（Flash-Next `fp16`、DeepSeek V4 Flash `fp8`）を報告する。
- 配線はフェーズ 0 で行い、フェーズ 0 の試験用の値（D13）はこの同じオプションの値として `gpu-test` ビルドにだけ登録する。KVarN プリセット値はフェーズ 1 で production の値として登録する。
- テール長は正規ロングオプション `--kv-cache-tail <N>`（256〜2048 の整数）で指定し、`--kv-cache` と同じ 4 つのパーサ（help 専用パーサを含む）に登録する。解析後の検証で、範囲外・非整数の値、KVarN プリセット（フェーズ 0 では試験用の KVarN 値）を選んでいないときの指定、Qwen3.8 27B 以外のモデルでの指定を起動時エラーにする。未指定ではテールトークンを追加しない（L = W）。`--kv-cache-tail` もフェーズ 0 で配線し、試験用の KVarN 値と組み合わせて G0 の測定に使う。
- 代替案: コマンドごとに別名を置くのはエイリアス禁止に反する。環境変数で選ぶのは production に環境変数スイッチを残さない方針に反する。フェーズ 3 まで配線を遅らせると、G1・G2 の `gufo bench` 測定で KVarN を選べない。テール長をプリセット名の接尾辞（`kvarn-k4v4-l1024`）にする方式は、値の組み合わせが増えて `--help` で範囲を示せず、同じ挙動を 2 通りに書ける余地を残す。

### D11. ポリシーの fingerprint とグラフ同一性にプリセットを含める

`QwenExecutionPolicy::Fingerprint()` の未使用ビットに KVarN 種別と K/V ビット幅・テール長 L（未指定を区別する）・スケール型を追加し、グラフ workload identity とテレメトリの双方に効かせる。FP16 の fingerprint 値は変えない。これによりプリセットをまたいだ HIP グラフの再利用が起きない。`UsesFp16AttentionKv()` を参照する既存の分岐（arena の平面選択、state ABI など）は、KVarN を FP32 経路と誤判定しないように全箇所を見直す。代替案: プリセットごとに別のポリシー型を作る方式は、経路判定の分岐を型で増やし保守負荷を上げる。

### D12. 見積と報告をプリセットに連動させる

- `QwenGpuArena::EstimateMemoryUsage` の KV 項を、KVarN 選択時は D5 のサイズ式（タイル数 ×（コード + スケール・ゼロ点 + 正規化スケール）+ sink/テール行）に置き換える。封印用の一時領域とチャンク用ワークスペースは既存スクラッチ内に収め、収まらない分だけ固定上限として見積に加える。
- テール長（未指定は「なし」）と、実効 bpv を「本体のみ」と「総量（sink・テール・スケール・ゼロ点を含む）」の 2 値で、起動ログの完了行と `gufo bench` の出力に報告する。`gufo diagnose` はモデルを読み込まないハードウェア診断であるため、報告先に含めない。
- 代替案: 既存の FP16 式に定数係数を掛ける方式は、報告値が受入基準と一致せず bpv 基準を検証できない。

### D13. フェーズ 0 は gpu-test 専用の疑似量子化で品質だけを測る

- `CMakeLists.txt` に疑似量子化を有効にするコンパイル定義のオプションを追加し、`CMakePresets.json` の `gpu-test` プリセットだけで有効にする。production（`release`）ビルドには含めない。
- 有効時は `--kv-cache` に試験用の値（候補プリセットごとの `pseudo-kvarn-k4v4` などの値、基準線 `baseline-q8`、`baseline-q4`）を登録する。これらの値は「封印 → 即時逆量子化 → 既存 FP16 KV 領域へ書き戻し」の経路を選び、既存の読み出し経路は変更しない。`fp16` を選んだ場合は既存経路と完全に同じ動作をする。
- 試験用の KVarN 値のテール長は `--kv-cache-tail` で指定し、未指定ではテールトークンを追加しない（L = W）。値の接尾辞でテール長を渡す方式は使わない（D10）。
- E_q8 / E_q4 の基準線は同じ枠組み（ブロック 32、FP16 スケール、回転あり、sink 128 行は F16）で実装する。基準線はテールを持たず、sink 以外の各行を書き込み直後に量子化する（llama.cpp の q8_0 / q4_0 KV と同じ扱い）。KVarN プリセットではないため、`--kv-cache-tail` を受け付けない。
- 疑似量子化はチャンクの q_max で封印するため、prefill 中の前置文脈の行は、ビュー規則より最大 1 チャンク分多く量子化値を読む。これは候補を不利にする方向の近似である。採点する位置は 1 トークンずつ decode し、ビュー規則どおりに読む。
- フェーズ 0 では KVarN のレイアウトを確保しないため、G0 のメモリ（テール長ごとの総量 bpv とセッションあたり KV 容量）は D5 のサイズ式による計算値として成果物に記録する。実確保量との一致はフェーズ 1（tasks 3.2）とフェーズ 4（T-09）で確認する。
- 品質評価ハーネスは Qwen のモデルツリー（`tests/models/qwen/` の gpu-test 実行ファイルと `tools/qwen27b/` の集計スクリプト）に置き、同一ビルドで `--kv-cache` と `--kv-cache-tail` の値だけを変えて教師と候補の全語彙 logits を得る。
- プリセット・適合テール長・スケール型・評価セット・δ・N を確定したら、確定値を本変更の spec・design・tasks に書き戻し、フェーズ 1 の終わりにコンパイル定義・試験用の値・疑似量子化経路を削除する。`--kv-cache-tail` は production のオプションとして残す。
- 代替案: 最初から本番読み出し経路を実装すると、G0 の go/no-go 判断前に大規模な作業を確定させることになる。環境変数で試験モードを切り替える方式は、環境変数スイッチを残さない方針と衝突する。

### D14. 品質評価は既存の一致トークン比較の枠組みを再利用する

`docs/TESTING.md` の一致トークン比較（トークン化は 1 回、同一履歴、各位置で全語彙分布）と `docs/BENCHMARKS.md` の KL/NLL 定義をそのまま使い、深度 4K / 32K / 128K の直後 256 位置、散文・コード・非英語を含むコーパスで評価する。成果物（モデル・教師ハッシュ、プロンプトとトークン列ハッシュ、設定、スキーマ版）を記録し、大容量 logits は Git 外に置く。

- コーパスは文書単位で連結する（文書を途中で切った断片は、高サプライズの位置を作ってテール統計を支配するため）。文書の順序を変えて 3 つのコーパスを作る。
- KVarN の各プリセットはテール長 未指定・256・1024・2048 の 4 通りで評価し、基準（D17）を全深度で満たす最小のテール長を適合テール長とする。
- 教師の平均 NLL が 5 を超える評価窓は、教師自身が予測できない乱数的な文字列などの窓で品質の信号にならないため、集計から除外する。この規則は G0 の再測定の前に事前登録したものである。全候補と基準線に同じ窓を同じように適用し、除外した窓（コーパス、深度、教師の平均 NLL）を成果物と報告に列挙する。

デコード型タスク評価は、正答率の差のブートストラップ 95% 区間が 0 を含み、下限が −δ を上回り、試行数 N 以上であることで判定する。代替案: 自由生成テキストの比較は最初の相違以降の誤差を分離できない（`docs/TESTING.md`）。独自の指標を新設すると既存の品質記録と比較できない。

### D15. 非有限値は既存の同期点で検出してリクエストを失敗させる

封印カーネルは非有限値を検出するとデバイス上のセッション別エラーフラグを立て、そのタイルの書き込みを完了させずに終了する。ホストは既存の同期点（logits の読み出し）でフラグを確認し、立っていればそのリクエストをエラーで終了させ、セッションを破棄してスナップショット化・再利用の対象から外す。ホスト同期は追加しない。代替案: 有限化して継続する方式は、上流の異常を隠し品質ゲートの非有限 0 件の判定を無意味にする。専用の同期点を追加する方式は、グラフ経路の性能とホスト同期禁止に反する。

### D16. 長時間の検証はタイムアウトで失われない実行方法で行う

G0 の品質評価（19 構成 × 3 コーパス × 深度 4K / 32K / 128K で約 14 時間）、T-08 / T-09 の本測定、一致性スイート、ベンチマークは、対話ツールの 1 回の呼び出しの上限（最大 2 時間、既定 2 分）を超える。フェーズ 0 の最初の測定では、呼び出しがタイムアウトして待機が中断された。これを避けるため、数分を超える検証は次の方法で行う。

- 起動: シェルから切り離したプロセスとして起動する（`setsid nohup <command> > <log> 2>&1 &`）。コマンドは開始時に全ジョブ数と見積時間、各ジョブの終了時に経過時間と残りジョブ数をログへ書き、終了時に終了コードを完了マーカーファイル（`<log>.done`）へ書く。対話ツールの 1 回の呼び出しの中で完了を待たない。
- 待機: 完了マーカーの出現をバックグラウンドの待機で待ち、1 回の待機の上限はツールの許容最大（2 時間）とする。上限に達したら、ログ末尾と生成済みの成果物数で進捗を確認し、プロセスが生きていれば待機を再開する。短い間隔での繰り返し確認はしない。
- 再開: 評価ハーネスは (候補, テール長, コーパス, 深度) の単位ごとに成果物を書き出し、既存の成果物があれば再計算せずに再利用する。教師 logits は Git 外の成果物ディレクトリにキャッシュし、再開時に再計算しない。途中で中断しても、完了した単位は失われない。集計は単位ごとの成果物から行う。
- 一致性スイートとベンチマークも、構成（プリセット、テール長、深度）ごとに結果を書き出し、同じ方法で再開できるようにする。
- 測定中は他の GPU ジョブを同時に実行しない（速度と所要時間の見積が崩れるため）。

代替案: 1 回の呼び出しで完了まで待つ方式は、2 時間を超える測定で必ず中断する。短い間隔で状態を確認し続ける方式は、待機のたびにコンテキストを消費し、測定の進行には寄与しない。一括の成果物を最後に 1 度だけ書く方式は、途中で中断すると数時間分の結果を失う。

### D17. 品質は q8→q4 内分位置で判定する

G0 の再測定（ラベル `g0-tail`、171 ジョブ）で、当初の基準（候補 ≤ E_q8 の許容幅ゼロの点推定、P99.9 ≤ 1.1 倍、top-1 ≥ E_q8 − 0.001）には次の欠陥があった。

- E_q8 自身の統計量が裾の少数位置に支配される。128K の平均 KL は差の 86% が上位 5 位置に集中し（その 5 位置を除くと差は −0.002）、P99.9 は線形補間で上位 2 位置の値になる。
- top-1 の 0.001 は 1 位置未満の差（n = 512〜768 で 0.5〜0.8 位置）で、標本誤差の内側を判定している。
- 中央値 KL の差は数値誤差と同桁（例: 32K の 7.3e-5 対 7.6e-5）で、許容幅ゼロの比較はコーパスの選び方で反転する（k4v4 の適合テール長は、コーパスの部分集合によって 256・2048・未指定に入れ替わった）。

新しい基準は、各判定指標 M（平均 KL、中央値 KL、大逸脱率 = KL が 1 nat を超える位置の割合、top-1 不一致率）について、深度ごとに 3 コーパスへプールした値から、候補が E_q8（0）と E_q4（1）の間のどこにいるかを測る。

- **p(M) = (M_候補 − M_E_q8) / (M_E_q4 − M_E_q8)**
- 品質優先: 適合テール長で全深度・全 4 指標が **p ≤ 0.15**。許容位置 0.15 は利用者が決めた（q8 から q4 へ向かう差の 15% まで劣化を許す）。
- メモリ優先: 適合テール長で全深度・全 4 指標が **p ≤ 1**（q4 以上）。
- P99.9 KL と NLL の差は記録するが、合否に使わない。
- M_E_q4 ≤ M_E_q8 となる深度・指標は p が定義できないため判定不能とし、G0 は未達とする（実測では 4 指標・3 深度のすべてで E_q4 が E_q8 を大きく上回り、分母は正である）。
- 1 nat は大逸脱の定数で、ツール側でファイル局所定数として宣言する。

**既存データ（g0-tail、除外窓 1 件）への適用結果**（最悪 p は深度・指標の最大。再測定なし）

| 構成 | 総量 bpv | 最悪 p | 律速 |
|---|---|---|---|
| `k6v5` L=2048 | 6.08 | 0.143 | 128K の大逸脱率 |
| `k5v5` L=2048 | 5.58 | 0.217 | 32K の大逸脱率 |
| `k6v5` L=1024 | 6.01 | 0.282 | 32K の平均 KL |

許容位置の感度: 0.10 では合格する構成がなく、0.15 では `k6v5` L=2048 だけが合格し、0.25 では `k5v5` L=2048 も合格し、0.50 では 7 構成が合格する。メモリ優先（p ≤ 1）は `k4v4` L=256 以上が合格し、未指定は 128K で不合格（1.09）になる。

**余裕が薄い点:** `k6v5` L=2048 の律速は 128K の大逸脱率で、768 位置中 E_q8 が 6 件、候補が 11 件、E_q4 が 41 件である。1 位置の増減で p が約 0.029 動き、許容できる超過は 5 位置までである（0.15 × 35 = 5.25）。`k4v4` L=256 も最悪 0.97 で余裕が薄い。したがって G0 の合格は暫定であり、T-08 の再判定で確定する。

**後付けの基準であることの扱い:** この基準は G0 の測定結果を見た後に定めた。結果に合わせた調整を防ぐため、(1) 許容位置 0.15 は固定し、T-08 の結果を見て変更しない、(2) T-08 は G0 で使っていない評価窓（別シードで文書順を変えた新規コーパス、各深度 6 窓以上）で再判定する、(3) p の窓単位ブートストラップ 95% 区間を併記する。G0 の 3 コーパスは同じ文書集合の並べ替えなので、新規コーパスも文書は重なるが、窓の内容は別になる。窓が深度あたり 2〜3 個しかない G0 の区間は楽観的で、判定は点推定で行う。

**長距離参照タスクを品質ゲートに加える理由:** 位置ごとの分析（`G0-ANALYSIS.md`）で、劣化が少数位置に集中し、32K の超過はすべて F16 テールの外にある遠距離参照の 16 位置から来ていた。128K の最大の超過成分は参照元が F16 で残っている近距離コピーの位置で、量子化された多数の遠方キーが注意の確率質量を奪う可能性があるが、原因は未確定である。教師強制の統計量はこうした位置を過小に拾うため、32K と 128K に置いた事実の参照タスクで直接確かめる（正答率の非劣性、δ_ret = 0.05 と N_ret = 128 は G0 で確定）。

代替案:
- 許容幅ゼロの点推定（当初の基準）は、上記の欠陥により、同等な候補でも通りにくい。
- 信頼区間による等価性検定は、窓が深度あたり 2〜3 個しかなく、位置単位のブートストラップは窓間の相関を扱えないため、G0 では判定の根拠にできない。T-08 の窓数で併記する。
- P99.9 の合否使用は、上位 2 位置で決まる統計量であり、E_q8 自身が 2.6〜12 の範囲で変動するため、採らない。
- 絶対値のマージン（例: 中央値 +5e-5）は、q8 と q4 の差という実測に紐づかず、深度ごとの厳しさも不揃いになる。
- 位置単位の除外（教師 NLL が高い位置）は、高 KL 位置の教師 NLL が 0〜25 に散らばり、結果に依存した除外になるため、採らない（窓単位の D14 は維持）。

### D18. 性能契約は Q8_0 で測り、深度 128K の速度向上は理想利得に対する割合で判定し、未達時は利用者に判断を仰ぐ

（2026-10-03 改訂: D19 により、深度 128K の理想利得による判定と品質優先プリセットの例外を廃止した。測定重み、FP16 を同じ系列で測ること、未達時の扱いは引き続き有効である。以下は決定の経緯として残す。）

G1 の 1 回目の判定（2026-10-03、`docs/models/qwen3.8-27b/G1-REPORT.md`、Q8_0、release ビルド）は未達だった。AR tg の FP16 比は深度 0 で 0.993、4K で 0.972〜0.983 と合格し、32K で 0.855〜0.936、128K で 0.640〜0.813 と 1.00 倍に届かなかった。同じ測定の pp は 24 点中 21 点が FP16 比 0.95 倍未満（0.82〜0.94。0.95 倍以上は L = 2048 の深度 0 の 3 点だけ）で、G2 の基準（全深度 0.95 倍以上）にも届いていない。当初の契約には次の欠落があった。

- 測定に使う重みを指定していなかった。`BENCHMARKS.md` は Q4 と Q8 の両方を掲載し、proposal の動機は Q4 の数値、G1 は Q8_0 で測った。
- メモリ優先プリセットの 128K の 1.15 倍は、到達可能な上限の見積なしに置いた値だった。G1 の測定では、Q8_0 で読み出しがメモリ帯域の下限で済んだ場合の上限が約 1.18 倍で、1.15 倍はその利得の約 81% にあたる。Q4 の参考値（2026-09-23 の HTTP 測定）では同じ 1.15 倍が理想利得の約 51% にあたり、重みによって厳しさが変わる。
- G0 と異なり、未達時の扱いを事前に決めていなかった。

決定（利用者、2026-10-03）:

- **測定重み:** 性能契約は Qwen3.8 27B の Q8_0 GGUF（G1 の `Qwen3.8-27B-Q8_0.gguf`）で測り、ファイルの SHA-256 を成果物に記録する。分母の FP16 KV は同じ測定系列で測り、別の系列の値を流用しない。
- **理想利得:** 深度 d の判定では、同じ系列の FP16 KV の測定から次を算出する。
  - n(d) = d + 64（tg128 中の平均文脈長。`gufo bench` の tg は深度 d のスナップショットを復元してから 128 トークンを生成し、pp とは別に測る）
  - B_FP16(d) = n(d) × 16 層 × 4 KV ヘッド × 256 × 2（K・V）× 2 byte
  - B_KVarN(d) = n(d) トークン時点の使用中領域（sink 128 行、テール容量 C 行、残りの位置の封印済みタイル）の D5 のサイズ式によるバイト数
  - BW = B_FP16(d) / (T_FP16(d) − T_FP16(0))（G1 の測定では FP16 の 128K の増分 35.8 ms が、1 トークンで読む KV 8.59 GB を約 240 GB/s で読む時間に相当し、増分が KV 読み出し帯域で決まることと整合する）
  - G* = T_FP16(d) / (T_FP16(0) + B_KVarN(d) / BW) − 1（KVarN の読み出しがメモリ帯域の下限で終わった場合の FP16 比の伸び）
- **深度 128K のメモリ優先プリセットの判定:** FP16 比 R が R ≥ 1 + f·G* を満たすこと。f = 0.5。当初の 1.15 倍をこの式で置き換える。他の基準（深度 0〜4K の 0.95 倍、32K 以上の 1.00 倍、pp・DFlash2・C8・起動時間・p99）は変えない。G1 の測定値に当てはめると、`kvarn-k4v4` の G* はテール長未指定で 0.184、L = 2048 で 0.181、閾値はそれぞれ R ≥ 1.092・1.090（tg 6.59・6.58 tok/s 以上、深度コスト約 22 ms 以下。1 回目は R = 0.813・0.809、深度コスト 73〜74 ms）となる。判定は再測定の値で行う。f = 0.5 は利用者が決めた。FP16 が帯域待ちの間に隠している softmax の計算時間は未測定で、f を高くするほど、KVarN の読み出しがその計算と展開をメモリ帯域の下限（約 10 ms）の近くで終えることを前提にすることになる。
- **未達時の扱い:** 性能契約の判定（G1、G2、G4 の T-09）で未達となった時点、または tasks 3.15 で予定した (a)〜(d) をすべて実施しても深度コストが予算に届かない時点で、作業を止める。測定値、原因の分析、考えられる次の選択肢を利用者に返し、判断を仰ぐ。利用者の判断なしに、基準の変更、予定外の最適化の継続、変更の中止を行わない。品質のゲート（G0、T-08）の扱いは D17 のまま変えない。
- **品質優先プリセットの例外:** `kvarn-k4v4` と `kvarn-k5v4` が深度 32K 以上で 1.00 倍に届き、品質優先プリセット `kvarn-k6v5` だけが届かない場合は、原因を調査する（tasks 3.16）。主因が実行ハードウェア（Strix Halo、gfx1151）と判定されたときは、その深度の基準を測定値と原因分析の記録で代え、README と `docs/CLI.md` に長文脈の速度を明記する。ハードウェアが主因であるとは、`kvarn-k4v4` に適用したのと同じ最適化を施した読み出しカーネルについて、次の 3 つがすべて成り立つことをいう。
  - H1: rocprofv3 のカウンタで測った律速資源（VALU 発行、メモリ帯域、LDS 帯域のいずれか）の利用率が、同じ機器で測ったマイクロベンチマーク上限の 80% 以上である。
  - H2: `kvarn-k4v4` との差が、5/6 bit 化で増える処理（追加ビット面の読み出しと展開）でおおむね説明でき、占有率の低下、レジスタのスピル、分岐の発散などの実装要因が主でない。
  - H3: 追加ビット面の展開が gfx1151 の命令で最小に近い。命令列と検討した代替案を記録する。D5 のビット面配置そのものが主因である場合は設計上の要因であり、ハードウェア起因とはしない。
  いずれかが成り立たない場合は、上の「未達時の扱い」に従う。

### D19. KVarN を KV メモリを減らす機能とし、長文脈の速度は FP16 比の下限ではなく基準値からの退行で判定する

D18 に従い G1 を 2 回目に判定し（2026-10-03、Q8_0、host ROCm 7.14、`artifacts/g1sys`、8 キーブロックの読み出し）、未達だった。AR tg の FP16 比は深度 0 で 0.996、4K で 0.974〜0.987、32K で 0.839〜0.926、128K で 0.605〜0.787 である。利用者が 1 回だけ認めた追加作業（D18）で次がわかった。

- キーのブロック化は効かない。キーごと処理（kKeyBlock = 1、(a)+(b) のみ）が最良で、`kvarn-k4v4` テール長未指定は 32K で 0.949、128K で 0.843、`kvarn-k6v5` L = 2048 は 32K で 0.808、128K で 0.631 だった。2・4・8 キーのブロックはブロックごとの最大値と再スケールの処理が増え、いずれもこれより遅い。kKeyBlock = 1 を採用した。
- KV をキャッシュに常駐させた計算だけの時間（文脈 2304〜9216 の 4 点を「クエリヘッド × キー」に対して直線で当てはめ、128K・16 層に換算）は、FP16 が 33.9 ms、`kvarn-k4v4` が 53.9 ms、`kvarn-k6v5` が 121.5 ms だった。FP16 の深度 128K の増分（約 35.6 ms）は、計算だけの時間とメモリ帯域の時間がほぼ同じで、両方が同時に限界に近い。
- したがって、キーごとにレーン間で縮約してオンライン softmax を進める今の注意カーネルの構造では、KV の読み出し量を減らしても速度は上がらない。KVarN は展開の計算が加わる分だけ FP16 より遅くなる。proposal の「読み出し量を縮めれば長文脈が速くなる」という前提は、この機器とこのカーネル構造では成り立たなかった。

決定（利用者、2026-10-03）: KVarN を KV メモリを減らす機能として出し、長文脈の速度が FP16 KV より下がることを受け入れて文書化する。

- **下限を残す項目:** 深度 0〜4K の AR tg（0.95 倍）、深度 0 の DFlash2 tg（0.95 倍）、C8 AR の合計スループット（0.95 倍、利用者あたり文脈 4096）、起動時間（悪化 5% 以下）。
- **基準値からの退行で判定する項目:** 深度 32K 以上の AR と DFlash2 の tg、全深度の pp。基準値は、その項目を最初に測る判定（AR の tg と pp は G1 の再判定、DFlash2 の tg は G2）で記録した、プリセット・テール長・深度ごとの FP16 比とする。以後の判定（G2、G4 の T-09）では、同じ点の FP16 比が基準値の 0.97 倍以上であること。pp は G1 の FP16 の前後 2 回で最大 2.4% ずれ、許容幅 3% に近いため、各点 3 回の測定の中央値で求める。tg は前後 2 回の差が 0.2% 以下なので 1 回とする。
- **p99:** 「封印ステップがレイテンシを突出させない」という元の意図に合わせ、KVarN のトークン間レイテンシの p99 / p50 が、同一負荷の FP16 KV の p99 / p50 の 1.05 倍以下であることとする。平均の速度は長文脈で下がるため、p99 の絶対値の比較では突出の有無を判定できない。
- **文書化:** プリセット・テール長・深度ごとの tg と pp の FP16 比を `docs/models/qwen3.8-27b/README.md` と `docs/CLI.md` に掲載し、KVarN が KV メモリを減らすための機能で、長文脈では FP16 KV より遅いことを明記する。得をするのは長文脈のセッションを複数並べる運用（262K あたり KV 16.0 GiB → 4.45〜6.08 GiB）で、負担するのは 1 セッションで長文脈を生成する使い方である。
- **D18 の扱い:** 測定重み（Q8_0）、FP16 を同じ系列で測ること、未達時に作業を止めて利用者に判断を仰ぐことは引き続き有効とする。深度 128K の理想利得による判定（R ≥ 1 + f·G*）と、品質優先プリセットの例外（H1〜H3、tasks 3.16）は廃止する。
- **読み出しカーネル:** tasks 3.15 の (d)（GQA の 6 ヘッドでのタイル共有）は行わない。レーンごとにキーを受け持つスコア計算や、GQA でのタイル共有など、softmax の構造を変える作り直しは本変更の範囲外とし、行う場合は別の change とする。

後付けの基準であることの扱い: この決定は G1 の 2 回の未達を見た後に行った。G1 の未達の記録（`G1-REPORT.md`、`BENCHMARKS.md` の KVarN 節、`EXPERIMENTS.md`）は残し、proposal の速度の主張を取り下げる。許容幅 3% と基準値の決め方は G1 の再判定の前に固定し、測定結果を見て変えない。

代替案:
- 記録だけにして合否に使わない方式は、以後の変更で速度がさらに下がっても検出できない。
- 今の測定値から固定の下限を置く方式は、結果を見てから下限を決めることになり、退行防止と同じ働きをより粗く行うだけになる。
- softmax の構造を変える試作を続ける方式は、FP16 自身の計算時間が 128K で約 34 ms あるため、FP16 と同等の読み出しにできても速度比は 1.00 倍前後にとどまる。それを超えるには FP16 の注意カーネルより少ない計算で済む構造が必要で、成功の見込みが低いため本変更では行わない。

- **DFlash2（G2）:** 基準の扱いは原因を確かめてから決める。G2 の診断（tasks 4.5）では、深度 0 の比 0.588 は、FP16 と KVarN で生成列が分かれた 1 本の軌跡の受理率の差（0.460 対 0.277、サイクル数 36 対 62）でほぼ決まり、1 サイクルの時間は同等（158.3 対 155.6 ms）だった。深度 0 の tg は 16 トークンの Prime から最大 128 トークンを生成するだけなので、受理率は 1 本の軌跡に大きく左右される。一方で受理率の差が大きいため、ドラフトへの入力特徴が KVarN の経路で正しく渡っていない可能性も残る。tasks 4.8 で、生成列が分かれる前のサイクルの比較と、コーパス全体での受理率の分布を測って切り分ける。深度 128K では 1 サイクルの時間が 283 → 678 ms（+139%）で、KVarN の DFlash2 は KVarN の AR より遅い。この点は README と `docs/CLI.md` に「超長文脈では AR を使う」と記載する。

代替案:
- 全範囲の 4.4 と T-08 を終えてから使い始める方式は、合わせて 60 時間を超え、目的に合わない。
- 確認なしで今すぐ使い始める方式は、利用者が使う `kvarn-k5v4` テール長 2048 の品質を、G0 の 1 回の評価窓だけで判断することになる。

### D21. 通常のテストでは複数セッションを同時に動かさず、専用スイートでだけ動かす

2026-10-04 の 4.8 の追跡で、投機検証と 2〜8 セッションのバッチ decode が KVarN の行を prefill 用ワークスペースへ書き、通常のテスト（3.13 の C2/C8、3.14 の DFlash2、`inference_backend_gpu_test` の並行判定）がそれを見逃すことが分かった。利用者は、通常のテスト（ctest の通常のプリセットと `tools/qwen27b/check.py` の通常のスイート）では複数セッションを同時に動かさず、複数セッションのテストは ctest のラベル `multi-session` と check.py の専用スイート `multi-session` にまとめ、明示的に指定したときだけ動かすと決めた（利用者、2026-10-04）。

- 対象は、1 回の呼び出しで 2 セッション以上を処理する経路（`ForwardTokenBatch`、`ForwardVerificationBatch`、`InjectTargetContextBatch`、`ForwardBlockBatch`）と、複数セッションを並行に走らせる検査とする。
- 通常のスイートのテストは `GUFO_MULTI_SESSION_TESTS` が未設定なら該当ブロックをスキップし、その旨を出力する。
- ctest の通常のプリセット（`gpu-full`、`gpu-fast`）はラベル `multi-session` を除外し、専用プリセット `gpu-multisession` がそのラベルだけを選ぶ。
- 1 セッションだけを通す本番入口の回帰テスト（`qwen27b.dflash-kvarn`）は通常スイートに置く。

## Risks / Trade-offs

- [Qwen 系の K 感度が高く品質目標に届かない] → G0 でビット幅を K 優先（`k5v4` / `k6v5`）へ上げ、テール長（最大 2048）で直近の行を F16 に残して補う。メモリ優先プリセットが G0 の基準に届かない場合は、G0 で本計画を再策定する。
- [浅い文脈で tg が劣化する] → sink・テールの読み出しを既存 FP16 経路に寄せ、タイル処理の占有率を調整する。浅い文脈の tg 基準は G1 で判定する。
- [封印ステップでレイテンシが突出する] → 封印は常時起動・述語付きで、実処理は 128 トークンごとに 1 回。p99 を G4 の性能評価で FP16 と比較し、必要なら層・ヘッド並列化で分散する。
- [読み出し経路の多さによる不整合] → D7 の共有ヘルパに D2 のビュー判定を集約し、T-03 の同一ケースを全経路に適用する。
- [ビュー規則の off-by-one] → e_t ≤ q − L − 1 の境界（位置 e_t+L と e_t+L+1）を T-03・T-05・T-07 の必須ケースにする。
- [HIP グラフ適格性の喪失] → D4 のデバイス側述語と D11 の fingerprint 更新。グラフ拒否理由が増えていないことをグラフテストで検査する。
- [スナップショット互換の破損・キャッシュ汚染] → D9 の版 3 と同一性キー。FP16 のキーとバイト列は変更前と一致することをテストで検査する。
- [教師強制評価がテールの効果を過大評価する] → デコード型タスク評価を必須ゲートにする。
- [テール長を大きくすると長文脈 tg の低下幅が増える] → 性能契約をテール長未指定と L = 2048 の両方で判定し、両方の FP16 比を文書に掲載する。
- [品質基準を G0 の結果を見た後に定めた] → D17 のとおり許容位置を固定し、T-08 を G0 と異なる評価窓で再判定して、区間を併記する。
- [品質優先の合格余裕が薄い（`k6v5` L=2048 の最悪 p = 0.143、128K の大逸脱率で 1 位置 ≈ 0.029）] → T-08 の新規窓で確定し、不合格なら再策定する（許容位置を動かさない）。
- [教師強制の統計量が遠距離参照の劣化を過小に拾う] → 長距離参照タスクを品質ゲートに加える（D17、tasks 6.2）。
- [既定（テールなし）では品質優先の基準を満たさない可能性がある] → 各プリセットの適合テール長を README と `docs/CLI.md` に明記し、テール長ごとの比較表を README に掲載する。
- [長時間の測定がツールのタイムアウトで中断し、結果を失う] → D16 の切り離し実行・単位ごとの成果物・再開で行う。
- [FP16 経路の回帰] → 回転と 3 領域読み出しは KVarN 選択時のみ有効化し、既定 `fp16` では既存カーネル経路をそのまま使う。既存のビット一致テストは変更しない。
- [ライセンス記録漏れ] → 参照実装から翻案した場合のみ `NOTICE`、`THIRD_PARTY_NOTICES.md`、`licenses/` を更新し、依存チェックを通す。
- [長文脈の KVarN 読み出しが計算律速で、FP16 KV より遅い（キーごと処理の採用後で `kvarn-k4v4` の 128K が 0.843、`kvarn-k6v5` が 0.631）] → D19 のとおり受け入れ、プリセット・テール長・深度ごとの FP16 比を README と `docs/CLI.md` に明記し、基準値からの退行で以後の悪化を検出する。
- [バッチ decode 経路の KVarN 未配線（投機検証バッチは G1 の作業中に修正済み、C2〜C8 の AR バッチ `ForwardTokenBatch` は未対応で、KVarN では FP16 平面が null のまま読み書きする）] → 全注意 launcher で KVarN ポリシーと null 平面の組み合わせを明示エラーにし、C2・C8 対 C1、DFlash2 対 AR の end-to-end テストで確認する（tasks 3.13・3.14）。演算子単体のテストだけでは呼び出し側の配線漏れを検出できない。
- [prefill の封印と読み出しで pp が下がる（G1 の測定で 24 点中 21 点が FP16 比 0.82〜0.94、テール長未指定は深度 0 でも 0.92 前後）] → tasks 4.7 でコストを分解してから G2 を判定する。
- [性能の測定条件の揺れ（G1 の 1 回目は `/nix` の容量不足で system の hipcc を使い、2 回目は FP16 の値を 1 回目から流用した）] → 公式ツールチェーンでビルドし、FP16 は同じ系列で測り直す（D18、tasks 3.17）。

## 解決済みの判断

- D-01 オプション名は `--kv-cache`（値 `fp16` またはプリセット名）。テール長は `--kv-cache-tail`（D10）。
- D-10 テール長はユーザーが `--kv-cache-tail` で 256〜2048 の整数を指定する。未指定ではテールトークンを追加しない（L = W）。上限 2048 は `kvarn-k4v4` の総量 4.6 bpv 基準（L ≤ 2432）から決めた（D1）。
- D-11 基準線 E_q8 / E_q4 はテールを持たず、sink 以外の各行を書き込み直後に量子化する。sink 128 行は KVarN と同じく F16 で保持する（D13）。
- D-12 教師の平均 NLL が 5 を超える評価窓を集計から除外する規則を、G0 の再測定の前に事前登録する（D14）。
- D-13 長時間の検証は、切り離し実行・単位ごとの成果物・再開・完了マーカーの待機で行う（D16）。
- D-14 品質は q8→q4 内分位置 p で判定し、品質優先は p ≤ 0.15、メモリ優先は p ≤ 1 とする。許容位置 0.15 は利用者が決めた。T-08 は G0 と異なる評価窓で再判定し、許容位置を変更しない（D17）。
- D-02 品質優先プリセットは `kvarn-k6v5`（K 6 bit・V 5 bit）。G0 の D17 判定（`kvarn_quality.py report --gate`、ラベル `g0-tail`）で `kvarn-k6v5` L=2048 の最悪 p は 0.143（128K の大逸脱率）で許容位置 0.15 以下となり合格。`kvarn-k5v5` L=2048 は 0.217 で不合格。
- D-03 適合テール長は `kvarn-k4v4`（メモリ優先）が 256、`kvarn-k6v5`（品質優先）が 2048。`kvarn-k5v4` はメモリ優先基準にテールなし（L = W）で適合する。適合テール長は、テール長 未指定・256・1024・2048 のうち、メモリ優先は p ≤ 1、品質優先は p ≤ 0.15 を全深度・全 4 指標で満たす最小の L とする。
- D-04 スケール類の数値型は FP16。G0 の観測で FP16 オーバーフローは 0 件、アンダーフローは各構成 167〜215 件で、いずれも ε 下限（1e-5 は FP16 の正規最小 6.1e-5 未満）とゼロ点に由来し、実データのダイナミックレンジ不足ではない。BF16 は仮数が 8 bit で全スケールの精度を落とすため採用しない。
- D-05 非劣性マージンは δ = 0.03（デコード型）、δ_ret = 0.05（長距離参照型）、最小試行数は N = 200、N_ret = 128。問題セットは、デコード型が数学推論 100 問とコード 100 問、長距離参照型が 32K と 128K に事実を置く 128 問とする。マージンは G0 の許容位置 0.15 と同じく利用者が許容する劣化の上限として固定し、試行数はブートストラップ 95% 区間が判定に足る幅になる最小規模とする。問題ファイルは 6.2 で固定し、SHA-256 を成果物に記録する。
- D-06 FP16 スナップショットから KVarN への変換復元は本変更に含めない（Non-Goals）。
- D-07 既定 `fp16` を維持する。
- D-08 27B のフル注意層数は 16（64 層 − MTP 1 層、`block_count = 65`、`tests/core/gguf_reader_test.cpp:267-320`）。実測確認済み: 配布 `Qwen3.8-27B-Q8_0.gguf` のメタデータは `qwen35.block_count = 65`、`qwen35.nextn_predict_layers = 1`、`qwen35.full_attention_interval = 4`、`qwen35.attention.head_count = 24`、`qwen35.attention.head_count_kv = 4`、`qwen35.attention.key_length = 256`、`qwen35.context_length = 262144` であり、読み取り結果は 65 − 1 = 64 層、`FullAttentionLayerCount() == 16`。`build/cpu-test/gguf_reader_test` は同値を期待値として通り（テスト 1.1）。
